# 웹 클래스 프로젝트 연계 커리큘럼과 개편 계획

기준일: 2026-10-20 · 구성 방향·프로젝트 범위·단원별 완료 기준 확정 · 후반 사례·배포 비교는 검토안 · 구현 착수 전

웹 클래스는 하나의 프로젝트를 기획하고 제작한 뒤, 화면과 동작을 개선하고 실제로 배포해 다른 사람에게 공유하는 과정이다. 수강자는 사이트 한 편과 함께, 무엇을 확인하고 왜 수정했는지 설명할 수 있는 판단 기준을 남긴다.

이 문서는 1~5단원의 목표와 기존 수업 개편 범위를 정한다. 수업 코드·완료 판정·지도·데이터 구조의 변경이나 외부 계정 생성·배포는 이번 작업에 포함하지 않는다. 기존 AI 입문 5수업과 제작 4단원 12활동을 구성의 뼈대로 사용하며, 활동 수 추가는 확정하지 않는다. 문서의 1단원은 AI 입문, 2~5단원은 기존 네 제작 과정에 대응한다. 기본 4월드와 선택 심화 1월드의 명칭·지도 체계 변경을 뜻하지 않는다.

| 미결 | 실제 공유가 어려운 사람의 대체 과제와 최종 완료 표기, 정식 회원 진도 저장 정책.                                   |

## 하나의 프로젝트가 발전하는 흐름

| 단원                  | 이어받는 것                          | 프로젝트에서 바꾸는 것                               | 다음 단원으로 넘기는 결과            |
| --------------------- | ------------------------------------ | ---------------------------------------------------- | ------------------------------------ |
| 1 AI 입문과 제작 준비 | 만들고 싶은 목적 또는 공통 연습 사례 | 작업 폴더를 준비하고 첫 파일을 제작·수정·실행한다.   | 작업 폴더와 직접 열어본 첫 HTML 화면 |
| 2 기획과 첫 제작      | 같은 폴더와 첫 파일                  | 실제 콘텐츠를 담아 제목·소개·목록·버튼을 구성한다.   | 자기 콘텐츠가 들어간 첫 초안         |

| 5 공개와 운영         | 같은 프로젝트의 배포할 파일          | 공개·접속·공유·수정·재배포를 수행한다.               | 실제 공유 주소와 마지막 개선 기록    |

처음에는 `index.html` 중심으로 시작한다. 이미지·스타일·스크립트 파일이 필요하면 같은 프로젝트 안에서 관리한다. 단원마다 새 폴더나 별도 예제를 실제 프로젝트로 다시 만들게 하지 않는다. 이전 기획·콘텐츠·요청·확인 기록은 이어받고, 수정할 필요가 생긴 항목만 갱신한다. 특정 파일 분리 방식과 기록 데이터 스키마는 구현 단계에서 정한다.

| 목적        | 기본 콘텐츠                                     | 상세 보기의 쓰임                        | 공유받은 사람이 해볼 행동             |
| ----------- | ----------------------------------------------- | --------------------------------------- | ------------------------------------- |
| 서비스 소개 | 누구를 돕는지, 제공 내용, 실제 다음 행동        | 범위·준비할 자료·제외되는 내용 살펴보기 | 어떤 도움인지 이해하고 제공 내용 찾기 |
| 포트폴리오  | 내 소개, 작업 목록, 직접 맡은 역할              | 문제·역할·해결 과정·배운 점 살펴보기    | 관심 작업을 열고 내가 맡은 역할 찾기  |
| 개인 사이트 | 좋아하는 주제, 실제 경험과 추천 내용, 관련 링크 | 추천 이유·사용 상황·아쉬운 점 살펴보기  | 항목을 선택하고 관련 정보 열기        |

주제가 없는 사람은 카피바라의 작은 쉼 모음 페이지로 원리를 연습할 수 있다. 공통 사례를 자기 경험이나 제작 성과로 표시하지 않는다. 핵심 설명은 처음부터 보여주고 상세 정보만 선택해서 읽게 한다. 콘텐츠가 짧거나 한 항목뿐이면 펼침·필터·저장을 억지로 추가하지 않는다.

## 1단원 AI 입문과 제작 준비

### 학습 목표와 활동

AI의 도움과 한계를 이해하고, 실제 도구에서 요청·결과 확인·수정을 수행한다. 코드 답변과 실제 파일 변경을 구분하며 자신이 작업 중인 폴더와 실행 화면을 찾을 수 있다.

| 기존 수업             | 유지                                             | 수정 또는 추가                                                                                         |
| --------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| AI 이해하기           | 역할·한계와 사람이 확인해야 하는 이유, 짧은 예시 | 이후 자기 프로젝트에서 AI에게 맡길 일과 사람이 판단할 일을 연결한다. 아직 설치·제작을 요구하지 않는다. |
| AI 종류와 도구        | 용도, 모델·도구·에이전트와 접속 방식의 구분      | 제품명 암기보다 실제 제작 도구를 선택할 때 필요한 구분으로 정리한다.                                   |
| 도구 준비하기         | Windows·Mac 안내, 컴퓨터 준비와 모바일 복습 구분 | 설치 확인을 작업 폴더 연결·파일 위치 확인까지 이어간다. 실제 지원 조건과 안내 화면을 다시 검증한다.    |
| AI와 첫 대화          | 요청, 결과 확인, 수정 요청                       | 이후 사이트에 쓸 소개나 콘텐츠를 소재로 활용하되 자기 기획을 미리 완성하도록 강제하지 않는다.          |
| 에이전트와 바이브코딩 | HTML 파일 제작·브라우저 실행·버튼 확인·수정      | 이때 만든 폴더와 파일을 2단원에서 그대로 사용함을 명시하고 실제 파일 실습을 보강한다.                  |

### 단원 결과와 확인 기준

컴퓨터 제작자는 작업 폴더에서 첫 HTML 파일을 열고, 요청한 변경이 파일·화면에 반영되는 것을 확인한다. 예시 복습자는 같은 흐름을 이해한 기록을 남긴다. 파일 없음·브라우저 대신 코드로 열림·예전 화면 노출 등 기존 도움말은 실제 환경에서 확인해 보강한다.

현재 구성의 활용도가 높다. 별도 새 입문 과정을 만들기보다 기존 다섯 수업과 다음 제작 단원의 접점을 다듬는다.

## 2단원 기획과 첫 제작

### 학습 목표와 활동

누구에게 무엇을 보여주고 어떤 행동으로 연결할지 정한 뒤, 실제 콘텐츠를 제작 요청과 첫 초안으로 연결한다.

| 활동               | 유지                                             | 수정 또는 추가                                                                                 |
| ------------------ | ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 기획과 자료 정하기 | 제목·대상·목적·소개·실제 콘텐츠, 목적별 예시     | 첫 범위를 소개·콘텐츠 목록·주요 버튼으로 좁힌다. 지금 필요한 자료와 나중에 채울 자료를 나눈다. |
| 제작 요청 다듬기   | 기획을 요청으로 연결하고 직접 편집한 요청을 보존 | 1단원의 같은 프로젝트를 수정하도록 안내한다. 바꿀 범위와 유지할 콘텐츠를 함께 지정한다.        |
| 첫 화면 확인하기   | 예시와 컴퓨터 제작 구분, 내용·버튼 확인          | 자기 파일에 실제 콘텐츠가 반영됐는지 확인하고, 누락·잘못된 내용은 한 번 수정한다.              |

### 단원 결과와 확인 기준

초안에서 페이지 목적을 이해할 수 있고 주요 내용이 맞으며 버튼이 의도한 위치로 연결된다. 디자인 완성을 요구하지 않는다. 첫 화면의 대표 캡처는 선택적으로 남기며 다음 단원의 비교 출발점으로 쓴다.

기존 세 활동을 유지한다. 같은 프로젝트 연결과 첫 초안의 수정·재확인 안내를 보강한다.

## 3단원 화면과 사용 경험

### 학습 목표와 활동

자기 초안을 방문자 입장에서 관찰하고, 중요한 문제를 좁혀 수정 요청을 작성한 뒤 전후를 확인한다.

| 활동                  | 유지                                   | 수정 또는 추가                                                                                                                            |
| --------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 두 화면에서 문제 찾기 | 모바일·PC 비교, 관찰을 문장으로 남기기 | 공통 너비 넘침 예시는 관찰 연습으로 사용한다. 실제 파일에 같은 문제가 있다고 가정하지 않고 위계·가독성·간격·버튼 중 중요한 문제를 찾는다. |
| 개선 요청 쓰기        | 관찰→구체적 요청, 목적별 판단 기준     | 수정할 부분과 유지할 부분을 명시한다. 중요한 한두 곳에 집중하고 전체 재생성을 기본으로 안내하지 않는다.                                   |
| 수정 전후 확인        | 같은 조건에서 비교, 기존 버튼의 재확인 | 같은 프로젝트 파일에 적용한다. 의미 있는 변화에 기존 화면 첨부·영역 표시·설명을 선택적으로 활용한다.                                      |

### 단원 결과와 확인 기준

모바일·PC에서 확인한 개선본과 수정 이유를 남긴다. 문제가 없다면 확인한 기준과 선택한 개선점을 기록한다. 실제로 없는 오류를 만들거나 정해진 오류 문장을 자기 관찰처럼 쓰게 하지 않는다. 전후 화면을 매번 필수 제출하게 하지 않는다.

현재의 관찰·요청·비교 구조는 유지하고, 고정 예시 중심에서 자기 초안 중심으로 무게를 옮긴다.

## 4단원 동작과 데이터

### 학습 목표와 활동

방문자의 선택에 따라 화면이 달라지는 동작을 만들고, 상태를 언제 어디에 남겨야 하는지 판단한다. 공통 실습은 항목 선택과 상세 보기이며 필터·검색·저장을 모든 프로젝트에 요구하지 않는다.

| 기존 활동        | 유지할 원리                                            | 목표 활동과 보강 내용                                                                                                                                         |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 입력과 화면 변화 | 입력·상태·표시의 관계                                  | 항목 선택→상세 표시→닫기 또는 다른 항목 선택을 공통 사례에서 확인하고 자기 페이지에 필요한 경우 적용한다.                                                     |
| 새로고침과 저장  | 표시와 보존의 차이                                     | 무엇을 저장할 이유가 있는지 먼저 판단한다. 필요하면 자기 파일에서 브라우저 저장과 실제 새로고침을 확인한다. 필요 없으면 이유를 남기고 무저장 동작을 유지한다. |
| 다른 기기와 서버 | 이 브라우저의 상태와 여러 사람이 함께 쓰는 정보의 차이 | 자기 페이지에서 다른 기기로 열었을 때 기대할 결과를 설명한다. 실제 서버 구축은 기본 과제에 포함하지 않는다.                                                   |

### 실습 범위와 확인 기준

기본 동작은 페이지 안에서 상세 내용을 펼치는 방식으로 안내한다. HTML 기본 기능으로 충분하면 그 방식을 사용할 수 있다. 공통 예시를 조작하는 것과 자기 파일에 동작이 반영된 것은 구분한다.

서비스는 제공 범위, 포트폴리오는 작업 과정, 개인 사이트는 사용 후기·추천 이유를 펼치는 사례로 연결한다. 핵심 정보는 접힌 영역에 숨기지 않는다. 자기 콘텐츠에 추가 동작이 불필요하면 공통 예시에서 원리를 익히고 적용하지 않은 이유를 남길 수 있다.

펼친 설명은 초기화해도 되는 경우가 많다. 나중에 볼 항목처럼 재방문 목적이 있는 상태는 저장 후보가 된다. 문의·신청 등 다른 사람에게 전달돼야 하는 정보는 브라우저 저장만으로 처리했다고 표현하지 않는다.

기존 저장 없는 비교와 저장 있는 비교를 모든 학습자가 반드시 조작하도록 하는 완료 조건은 수정 대상이다. 상세 보기의 확인, 저장 필요 여부와 범위의 판단을 중심으로 원고와 판정을 함께 재설계한다. 기본 과정에서 로그인·댓글·결제·공유 DB를 새로 구축하지 않는다.

## 5단원 공개와 운영

### 학습 목표와 활동

같은 프로젝트를 실제 배포하고 다른 사람에게 공유한다. 수정한 파일을 기존 배포 프로젝트에 다시 반영하고 같은 대표 주소에서 확인한다.

| 기존 활동         | 유지                                           | 수정 또는 추가                                                                                                                                     |
| ----------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 공개 전 점검      | 두 화면 확인, 주요 버튼, 공개 가능한 자료 판단 | 자기 파일의 핵심 흐름과 임시 문구·링크·이미지·공개 범위를 확인한다. 배포할 파일과 필요한 자산을 같은 폴더에 모은다.                                |
| 주소와 배포       | 로컬 주소와 외부 주소의 차이                   | 실제 계정·프로젝트 준비, 파일 업로드, 공개 설정, 공유할 대표 주소 확인을 안내한다. 로그인하지 않은 환경과 다른 기기에서 접속·핵심 동작을 확인한다. |
| 공개 후 문제 해결 | 상황·행동·기대·실제 결과와 수정 후 재확인      | 한 사람에게 주소와 확인할 행동을 전달한다. 피드백 또는 자기 점검으로 개선 한 가지를 선택해 수정·재배포하고 같은 주소에서 확인한다.                 |

### 공유와 재배포

서비스 소개는 제공 내용 찾기, 포트폴리오는 관심 작업과 역할 확인, 개인 사이트는 관심 항목과 관련 정보 확인처럼 부탁할 행동을 하나로 좁힌다. 실제 공유는 목표에 포함하되 상대의 답장을 완료 조건으로 두지 않는다. 상대 이름·대화 캡처 제출도 요구하지 않는다.

실제 문제가 없으면 의미 있는 콘텐츠 개선으로 재배포를 연습한다. 현재 예시의 고장 난 버튼을 모든 자기 프로젝트에 있는 문제로 취급하지 않는다. `file://`·`localhost`·공유할 웹 주소를 구분하고, 로그인한 소유자만 열 수 있는 주소를 공개 성공으로 기록하지 않는다.

4단원에서 저장을 적용했다면 다른 기기에서 선택 상태가 달라질 수 있음을 다시 확인한다. 웹페이지 배포가 각 방문자의 브라우저 저장 데이터를 공유하는 기능은 아니다.

### 배포 도구의 결정 경계

기본 안내는 폴더 업로드형 정적 호스팅을 우선 검토한다. 기존 [실습 안내](workbook-practice-guides.md)는 Vercel Drop을 사용하며, 최근 논의의 Netlify Drop은 추가 후보다. 서비스 교체는 확정하지 않았다. 기본 경로 하나를 선정하기 전에 실제 계정의 이용 조건·공개 설정·기존 프로젝트 갱신·Windows와 Mac 파일 준비를 검증한다.

[Netlify 공식 안내](https://docs.netlify.com/start/quickstarts/netlify-drop-quickstart/)는 폴더 배포·기존 프로젝트 업데이트와 계정 조건별 공개 범위를 설명한다. 2026-10-18 논의에서 문서를 확인했으나 학습자 계정으로 배포를 완료한 검증은 별도로 필요하다. 비용·소요 시간을 보장하지 않는다. 유료 도메인·Git 연동·자동 배포는 기본 완료 조건에 넣지 않는다.

### 단원 결과와 확인 기준

공유할 대표 주소를 기록하고 로그인하지 않은 환경과 다른 기기에서 주요 내용·동작을 확인한다. 한 사람에게 실제로 공유하고 수정 한 가지를 기존 배포 프로젝트에 반영한 뒤 같은 주소에서 재확인한다. 기록은 주소·확인 내용·공유 여부·마지막 개선 정도로 제한한다. 자동 URL 검사·외부 도구 조작·자동 배포는 별도 기능이며 이번 기획으로 추가하지 않는다.

현재 구현은 예시 완료 후 실제 적용을 선택 기록으로 분리한다. 목표 구성에서는 예시 학습은 계속 허용하되 실제 프로젝트 완료를 별도로 분명히 표현해야 한다. 기존 퀴즈·선행 조건과 전체 완료 판정을 즉시 변경하라는 지시가 아니며, 표시와 판정의 구체적인 설계가 선행돼야 한다.

실제 공유가 어렵거나 외부 서비스 준비가 막힌 경우 학습 확인과 남은 제작 작업을 보여준다. 대체 과제만으로 실제 공유 완료로 표시할지는 미결이다. 회신·추천·실제 고객 확보는 완료 조건이 아니다.

최종 정리는 첫 목적→첫 초안→화면 개선→동작과 저장 판단→공유 주소와 마지막 개선으로 연결한다. 단원마다 같은 내용을 새로 입력하지 않고 기존 기록을 가져온다. 영역 표시·화면 첨부는 보조 기록으로 유지하며 댓글·수집품·작업실 활동을 제작 완료 조건에 포함하지 않는다.

## 프로젝트 범위와 단원별 완료 기준 — 2026-10-20

이 절의 프로젝트 범위와 단원별 기준은 2026-10-20 사용자 승인으로 확정했다. 한 페이지 소개·모음 사이트, 공통 소재로 직접 만든 연습 프로젝트의 인정, 3단원의 근거 있는 유지 판단, 4단원의 근거 있는 기능 생략을 포함한다. 기존 화면·선행 조건·완료 판정은 아직 변경하지 않았으며, 아래 상태 이름은 UI 확정 문구나 데이터 스키마가 아니다. 공유 대체 과제와 배포 서비스는 미결이다.

### 기본 프로젝트의 범위

**한 방문자가 페이지의 목적을 이해하고, 관심 있는 내용을 찾고, 안내된 다음 행동을 할 수 있는 한 페이지 사이트**를 기본 범위로 삼는다. `index.html`에서 시작해 같은 폴더의 콘텐츠·화면·필요한 동작을 발전시킨다. 파일 분리나 부가 페이지가 생겨도 기존 프로젝트를 이어간다.

| 목적        | 첫 초안에 담을 내용                                           | 방문자에게 부탁할 확인 행동                   | 기본 범위에서 다루는 상세 정보  |
| ----------- | ------------------------------------------------------------- | --------------------------------------------- | ------------------------------- |
| 서비스 소개 | 누구에게 어떤 도움을 주는지, 실제 제공 내용, 가능한 다음 행동 | 필요한 제공 내용을 찾고 다음 행동의 의미 확인 | 제공 범위·준비할 자료·제외 내용 |
| 포트폴리오  | 내 소개, 실제 작업, 맡은 역할, 관련 링크가 있으면 연결        | 관심 작업을 찾고 내가 맡은 역할 확인          | 작업의 문제·과정·결과·배운 점   |
| 개인 사이트 | 주제 소개, 직접 고른 항목, 설명과 관련 링크                   | 관심 항목을 찾고 추천 이유나 관련 정보 확인   | 경험·사용 상황·추천 이유·한계   |

콘텐츠 개수나 섹션 수를 공통 통과 조건으로 고정하지 않는다. 실제 내용으로 방문자 행동을 확인할 수 있으면 된다. 아직 없는 서비스·실적·고객 반응을 채우지 않는다. 제공 내용이 계획이라면 계획임을 표시하고, 실제 신청 수단이 없으면 신청 가능한 것처럼 안내하지 않는다. 외부 링크를 쓸 때는 실제 도착지를 확인하고, 페이지 안 이동이면 도착할 내용이 있어야 한다.

포함할 과제는 내용 구성, 읽기와 탐색 개선, 필요한 상세 보기, 저장 필요 여부 판단, 정적 사이트 배포·공유·재배포다. 로그인·회원별 저장·댓글·결제·신청 접수 시스템·서버와 공유 DB 구축은 기본 프로젝트에 포함하지 않는다. 기존 외부 연락 수단의 링크를 연결하는 것과 접수 기능을 직접 만드는 것을 구분한다. 프레임워크 도입·유료 도메인·Git 자동 배포도 공통 완료 조건으로 요구하지 않는다.

공통 카피바라 사례로 연습한 사람은 학습 확인을 남길 수 있다. 자기 폴더에 공통 소재로 사이트를 직접 만들고 수정·공개했다면 제작 사실은 기록하되, 내용이 공통 연습 사례임을 표시한다. 예시를 누른 것만으로 직접 제작했다고 표시하지 않는다. 공통 사례로 직접 제작·공개·공유·재배포한 사이트도 연습 프로젝트로 인정한다. 단순 예시 조작과 구분한다.

### 완료를 판단하는 방식

**원리를 배운 것, 자기 파일에서 확인한 것, 끝까지 공개한 것을 따로 보여준다.** 앞 단원에서 확보한 결과를 이어받되, 단원 기록의 유무만으로 현재 파일의 상태를 추정하지 않는다.

| 구분           | 인정할 근거                                                                                | 구분해야 할 상태                                                   |
| -------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 학습 확인      | 설명·확인 문제·공통 예시를 통해 해당 원리와 판단을 확인                                    | 실제 파일 미적용이어도 학습 확인 가능. 이것만으로 제작 완료는 아님 |
| 실제 적용·확인 | 자기 프로젝트에서 아래 단원의 행동과 결과를 직접 확인했다는 본인 기록                      | 단순 시도·미해결 문제 기록과 목표 결과 확인을 구분                 |
| 프로젝트 완료  | 같은 프로젝트의 내용·화면·필요 동작과 저장 판단, 외부 접속·실제 공유·수정 후 재배포를 확인 | 예시 학습이나 URL 입력만으로 부여하지 않음                         |

현재 적용 기록은 문제가 남아 있어도 확인 사실을 남길 수 있다. 따라서 기존의 ‘직접 적용·확인 · 본인 기록’을 새 목표의 성공 판정으로 그대로 재사용할 수 없다. 후속 판정 설계에서 **한 일과 확인 결과, 남은 문제**를 구분해야 한다. 모든 외부 결과는 본인 확인이며 자동 검사·인증이 아니다.

### 기본 경로 제안

**후속 결정: Vercel Drop을 기본 후보로 둔다.** 2026-10-20 사용자 승인으로 기본 후보를 Vercel로 정했다. 최종 도입과 실제 환경 검증은 남아 있다. 사용자가 Vercel 선호를 제시해 기존 Netlify 우선 제안을 재검토했다. Vercel도 첫 폴더 업로드와 기존 프로젝트의 production 재배포를 지원하므로 이번 정적 사이트 과제의 기술 요구를 충족한다 [V1]. 기존 실습 안내를 보강해 이어갈 수 있다는 점도 이 저장소의 교육 운영상 이점이다. 초보의 사용성이나 안정성이 Netlify보다 우수하다고 실험한 결론은 아니다.

Vercel Hobby의 비상업적 개인 용도 제한은 그대로다. 실제 상품·서비스 판매 홍보는 Pro/Enterprise 대상이다 [V2]. 따라서 **모든 목적을 무료 Vercel로 공개할 수 있다**고 약속하지 않는다. 비상업적 개인 연습은 Hobby 조건을 확인하고 진행하며 실제 서비스 홍보는 목적에 맞는 플랜 또는 다른 호스팅을 별도로 확인하는 분기가 필요하다. ‘연습’ 문구만 붙여 실제 상업 목적을 바꾸었다고 간주하지 않는다. 유료 가입은 공통 완료 조건으로 요구하지 않는다.

기본 후보는 Vercel로 정하고 이용 목적별 조건과 실제 환경을 검증한다. Netlify는 비교 자료로 보존하며 공통 무료 경로를 보장하지 않는다. 기존 Netlify 우선 제안은 이 결정으로 대체하며 비교표의 공식 사실은 보존한다. [Vercel Pro 공식 안내](https://vercel.com/docs/plans/pro-plan)도 확인했으나 유료 가격표를 수업의 고정 조건으로 추가하지 않았다.

학습자는 본인 계정의 이용 목적·요금제·공개 범위를 확인하고 완성된 정적 폴더를 업로드한 뒤 production 대표 주소를 사용한다. 수정은 계속 자기 컴퓨터의 같은 폴더에서 하고 기존 배포 프로젝트를 갱신한다. 호스팅사의 AI 편집을 중간에 섞는 기능은 기본 실습에 포함하지 않는다. 사이트 이름·도메인은 재배포 연습 중 유지한다. 아래 검증 계획은 두 후보에 적용하며 특정 서비스의 실제 검증 완료를 뜻하지 않는다.

콘텐츠 보강량은 4·5단원이 크지만 학습 순서를 뒤집지는 않는다. 후반의 성립 조건을 먼저 확인하고, 본문은 앞 단원부터 연결한다. 기간·인원·성과 수치는 확정하지 않는다.

| 로컬 완성·배포 막힘       | ‘로컬 제작을 확인했어요. 공개는 [막힌 단계]에서 준비 중이에요.’           | 조건·파일·오류를 확인. 실제 공개 완료로 표시하지 않음          |
| 공개됐지만 접속 확인 부족 | ‘배포한 주소가 있어요. [비로그인/다른 기기] 확인이 남았어요.’             | 확인하지 않은 접속 범위로 복귀                                 |
| 공개·재배포 후 공유 못 함 | ‘공개와 재배포를 확인했어요. 타인 공유는 아직 대기 중이에요.’             | 공유 대체 과제와 최종 표기는 미결. 프로젝트 완료로 올리지 않음 |
| 공유했지만 회신 없음      | ‘주소와 확인할 행동을 전달했어요. 자기 점검으로 개선을 이어갈 수 있어요.’ | 상대 회신 없이 의미 있는 수정·재배포 가능                      |
| 로컬만 수정               | ‘수정 파일을 확인했어요. 대표 주소의 최신 반영은 아직 확인 전이에요.’     | 기존 배포 프로젝트 갱신·같은 주소 재확인                       |

상태별 문구는 표시 설계 검토안이다. 공개 실패와 공유 대기를 학습 이해 부족으로 해석하지 않는다. 실제로 확인하지 않은 일을 완료로 표시하지 않는 원칙을 유지한다.

### 클래스 최종 정리 원고

**제목: 같은 사이트를 어떻게 발전시켰나요?**

처음 만든 파일에 내 기획을 담고, 화면과 필요한 동작을 판단했어요. 지금까지 남긴 결과와 아직 확인할 일을 함께 살펴봐요.

결과 순서는 다음과 같다.

1. **내가 정한 목적과 내용:** 대상·방문자의 행동·실제 콘텐츠. 공통 연습 소재는 그 출처를 표시.
2. **첫 파일과 초안:** 같은 폴더에서 무엇을 만들고 어떤 내용을 반영했는지.
3. **화면의 판단:** 관찰과 개선 결과 또는 두 화면에서 유지한 이유.
4. **동작과 저장의 판단:** 필요한 기능·적용 결과·생략 이유·브라우저 범위.
5. **공개와 마지막 개선:** 대표 주소·비로그인/다른 기기 확인·실제 공유·수정 후 같은 주소 재배포.

첫 화면에는 확인된 결과와 **지금 이어갈 일 하나**를 우선 보여준다. 파일 실습이 없으면 첫 파일, 해결하지 못한 핵심 문제가 있으면 해당 확인, 공개 이후라면 접속·공유·재배포 중 남은 행동으로 안내한다. 모든 학습을 다시 풀거나 같은 기획을 재입력하게 하지 않는다. 임의로 새로운 필수 작업을 만들지 않는다.

모든 목표를 확인한 경우의 원고:

> 같은 프로젝트를 기획하고 제작한 뒤 공개·공유·수정 후 재배포까지 확인했어요. 무엇을 개선하고 무엇을 유지했는지, 어떤 기능을 생략했는지 설명할 수 있어요. 아래는 본인이 확인한 결과이며 자동 파일 검사나 외부 성공 인증이 아니에요.

일부가 남은 경우의 원고:

> 학습한 내용과 실제로 확인한 결과를 모았어요. [남은 단계]를 이어가면 같은 프로젝트의 다음 결과를 확인할 수 있어요.

정식 수료증·자격 인증·고객 확보·조회수·매출은 약속하지 않는다. 작업실·수집품·캘린더·선택 심화 완료를 기본 프로젝트의 필수 조건에 포함하지 않는다. 기기·계정 제약이 있는 사람의 대체 과제와 최종 명칭은 계속 미결이다.

### 클래스 소개 원고

이하 문구는 개편 후 안내할 **목표 원고**다. 현재 제공 상태를 설명하는 소개에 즉시 붙여 넣지 않는다. 실제 구현·환경 검증이 끝난 범위만 제공 중으로 말해야 한다. 가격·이용 기간·판매 상태는 기존 정책을 그대로 따른다.

**표제**

바이브코딩 웹개발 클래스

**핵심 소개**

AI와 첫 웹페이지를 만들고, 확인하고, 공개해요.

**설명**

AI를 거의 써보지 않았어도 작은 요청부터 시작해요. 같은 폴더에서 첫 HTML을 만들고, 내 기획과 콘텐츠를 담고, 화면과 필요한 동작을 다듬어요. 공개한 주소를 다른 사람에게 공유하고 수정한 내용을 다시 반영하는 과정까지 이어가요. 결과를 받아보는 데서 그치지 않고 **무엇을 확인하고 왜 바꿨는지 판단하는 방법**을 익혀요.

**만들 결과**

서비스 소개·포트폴리오·개인 관심사 중 하나를 담은 한 페이지 소개·모음 사이트를 만들어요. 주제가 없으면 공통 소재로 직접 연습할 수 있어요. 필요한 경우 페이지 안 상세 보기와 관심 표시 저장을 적용하고, 불필요하면 이유를 남겨 생략해요. 로그인·결제·서버 구축은 기본 과제에 포함하지 않아요.

| 단원                  | 소개 목차 문구                                                | 목표 결과                           |
| --------------------- | ------------------------------------------------------------- | ----------------------------------- |
| 1 AI 입문과 제작 준비 | AI의 역할과 한계·도구 준비·요청과 수정·첫 파일 열기           | 작업 폴더와 첫 HTML                 |
| 2 기획과 첫 제작      | 대상과 목적·실제 콘텐츠·기존 파일 수정 요청·초안 확인         | 내 기획이 담긴 초안                 |
| 3 화면과 사용 경험    | PC·모바일 폭 관찰·필요한 개선 또는 유지 판단·같은 조건 재확인 | 두 화면에서 확인한 초안과 판단 이유 |
| 4 동작과 데이터       | 필요한 상세 보기·저장 여부 선택·동작 확인·다른 기기 기대      | 기능 적용 또는 생략 판단과 결과     |
| 5 공개와 운영         | 공개 전 점검·Vercel 기준 배포·외부 접속·공유·수정 후 재배포   | 실제 대표 주소와 마지막 개선 기록   |

단원 번호는 학습 설명을 위한 구분이며 지도·월드 개수를 바꾸지 않는다. 기존 AI 입문 5수업과 제작 4단원의 각 3활동을 뼈대로 유지한다. 여러 기술 주제를 별도의 수업 개수로 과장하지 않는다. 기존 선택 심화는 기본 과정·완료와 구분하고 이용 가능 상태만 안내한다.

**이런 분을 위한 과정**

- AI와의 대화부터 파일 제작·확인까지 차근차근 경험하고 싶은 사람.
- 소개·포트폴리오·관심사 페이지를 작게 만들고 직접 고쳐보고 싶은 사람.
- AI의 완료 메시지만 믿기보다 실제 내용·화면·동작을 확인하는 방법을 배우고 싶은 사람.

**환경과 결과의 범위**

제작 실습은 개인 컴퓨터에서 진행해요. Windows·Mac 안내를 준비하고 모바일은 설명과 예시 복습에 활용해요. 모바일에서 예시를 본 것과 자기 파일을 만든 결과는 구분해요. 도구의 설치·계정·이용 가능 범위는 사전에 확인해야 해요. 두 OS의 실제 안내 검증은 제공 전 완료해야 하며 전 기기·OS 버전 지원을 약속하지 않아요.

배포 기본 후보는 Vercel이에요. 계정과 프로젝트 목적에 맞는 이용 조건을 확인해요. 비상업적 개인 학습과 실제 서비스 홍보의 조건은 다르고, 모든 목적을 무료로 공개할 수 있다고 약속하지 않아요. 유료 도메인이나 자동 배포는 기본 과제가 아니에요. 이 문단은 기존 공식 비교·5단원 원고의 조건을 요약하며 새로운 서비스 기능 검증을 뜻하지 않는다.

**학습과 완료 안내**

설명·예시로 원리를 익히는 학습 확인, 자기 파일에서 행동과 결과를 확인하는 실제 적용, 실제 공유·재배포까지 이어간 프로젝트 완료를 구분해요. 예시만 마쳐도 배운 내용을 정리할 수 있지만 실제 사이트 제작·공개 성공으로 표시하지 않아요. 기능이 필요 없다면 생략할 수 있고, 공유한 상대의 답장은 필요하지 않아요. 계정·배포·기기·공유가 막히면 확인한 결과와 남은 작업을 따로 보여줘요.

## 실제 화면 반영 작업 순서와 변경 범위 — 2026-10-20 검토안

사용자가 완료 요약·클래스 소개 구성을 승인하고 구현 계획 정리를 요청했다. 이 절은 **현재 코드를 대조한 실행 계획**이며 구현 착수 지시가 아니다. 원고의 내용 방향은 승인됐지만 상태 스키마·기록 연결·선행 판정·기존 기록 무효화 방식은 아래 검토 후 확정해야 한다. 이번에는 문서만 변경한다.

### 구현의 경계

목표는 같은 프로젝트의 1~5단원 원고와 확인 행동, 단원·최종 요약, 클래스 소개를 일치시키는 것이다. 기존 AI 입문 5수업·제작 4단원 각 3활동·지도와 캐릭터·선택 심화의 구조를 보존하는 방향으로 진행한다. 지도 수·새 월드·회원 인증·DB·영구 진도 저장·자동 URL 검사·자동 배포·메시지 전송·판매/결제·보상 확장은 포함하지 않는다.

학습 순서는 그대로 두되 구현은 **판정 계약→공통 상태→앞 단원→분기가 큰 후반 단원→요약과 소개→전체 검수** 순으로 진행한다. 실제 외부 실습은 로컬 UI 검수와 분리하며 계정·파일·공개 범위를 확보한 별도 실행이 필요하다. Vercel은 기본 후보이고 실제 환경 검증 완료를 구현 계획으로 대신하지 않는다.

### 구현 전 제시할 최소 상태·화면 설계 산출물

필드 이름이나 타입은 아직 확정하지 않는다. 다음 의미를 어디서 소유하고 어떻게 연결할지 작은 설계안으로 먼저 제시한다.

- 동일 프로젝트의 목적·내용과 각 단원 결과 연결. 현재 1단원 practice와 제작 applications의 결과를 중복 확인 없이 이어받기.
- 예시 학습 결과와 실제 파일 목표 확인의 출처, 진행 중/문제 남음/확인 결과.
- 3단원 개선/유지 판단과 해당 분기의 필수 확인.
- 4단원 상세 보기 적용/생략과 저장 적용/생략, 각각 이유·행동·결과·기기 범위.
- 5단원 공개 준비·배포·비로그인/다른 기기·실제 공유·로컬 변경·같은 주소 반영의 독립 결과와 막힌 단계.
- 기록 수정 때의 재확인 영향, 지도 학습 진도와 최종 프로젝트 상태의 연결, 방문 메모리 수명.

새 스키마·공통 상태 구조는 저장소 규약상 중요한 갈림길이다. **구체적인 설계안을 검토받은 뒤** 구현한다. 이번 기획 승인만으로 회원 저장·영속화·외부 API를 추가하지 않는다.

### 검수 범위와 마감 기준

각 묶음은 관련 순수 판정 테스트와 사용자 여정 검사를 통과한 뒤 다음 묶음으로 진행한다. 컴포넌트 문구를 그대로 복제한 단위 테스트보다 분기·판정과 실제 사용자 경로를 검사한다. 최종에는 전체 pnpm check·pnpm test:e2e·자체 코드 리뷰·PC/모바일 실제 브라우저 디자인 체크를 마친다. 디자인 체크는 기존 포괄 승인으로 재질문 없이 진행한다.

필수 여정은 예시만 학습해 실제 완료가 생기지 않는 경로, 같은 프로젝트의 실제 적용 경로, 3단원 유지, 4단원의 네 조합, 미해결 문제, 5단원 배포/접속/공유/재배포 대기·회신 없음, 수정 후 확인 무효화·기록 보존, 지도 왕복·새로고침 정책, 소개 직접 진입과 다음 행동이다. PC·모바일과 키보드·좁은 화면에서 기능 생략이 막다른 길을 만들지 않는지 확인한다.

자동 E2E는 외부 결과를 본인 확인으로 입력하는 UI 경로만 검증하며 실제 설치·배포·공유 성공 증거가 아니다. 학습자 Windows/Mac의 파일 생성→기획 반영→두 폭 확인→필요 동작→Vercel 첫 배포/기존 프로젝트 갱신→비로그인/다른 기기 접속·공유는 허용된 실제 환경에서 별도 검증한다. 검증하지 못한 서비스·기기 조건은 잔여로 보고하고 성공 약속을 발행하지 않는다.

각 묶음마다 변경·확인·한계를 보고한다. 사용자가 완성이라고 판단하기 전 커밋하지 않으며 머지 전 저장소 완료 조건을 충족한다.

## 상태·화면 분기·선행·재확인의 구체 설계안 — 2026-10-20

이번 사용자 요청에 따른 **검토용 설계안**이다. 실행 순서는 승인됐으나 아래 상태 이름·필드 의미·선행·재확인 정책은 아직 구현하지 않는다. 이 절이 앞 작업 계획의 추상적인 상태 계약을 구체화한다. 현재 제품 동작과 다른 부분은 승인 후 반영 대상이다.

### 1. 세 층을 서로 다른 값으로 관리한다

**학습 확인, 자기 프로젝트의 실제 결과, 전체 프로젝트 완료를 분리**한다. 예시 완료가 실제 결과를 만들지 않고, 결과·문제 문장을 작성했다는 사실도 목표 성공을 만들지 않는다.

| 층        | 소유할 의미                                                      | 화면 표기                                                                                                            |
| --------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 학습      | 각 수업·활동의 원리 확인. 미시작/학습 중/학습 확인               | ‘학습 확인’. 예시로 확인한 항목은 ‘예시 학습’, 실제 도구에서 원리까지 확인한 항목은 ‘컴퓨터 실습에서 학습’ 출처 병기 |
| 실제 적용 | 같은 프로젝트의 단원별 확인 항목·분기·근거·막힌 단계·현재 유효성 | ‘내 프로젝트 · 본인 확인’. 미진행/진행 중/확인 대기/목표 결과 확인/재확인 필요                                       |
| 프로젝트  | 전체 학습과 실제 적용의 현재 유효한 결과로 계산                  | ‘프로젝트 진행 전/진행 중/남은 확인/완료 · 본인 확인’ 또는 ‘완료 후 재확인 필요’                                     |

예시 학습과 실제 작업은 배타적인 모드가 아니다. 한 사람이 예시로 원리를 익힌 뒤 같은 단원에서 실제 파일을 확인할 수 있다. 경로를 바꿔도 다른 경로의 기록을 지우지 않는다. 본인 확인의 출처는 자동 검사·인증과 구분한다.

**프로젝트 완료의 제안 계약:** AI 입문 5수업과 제작 4단원 학습 확인, 아래 1~5단원 실제 목표 항목의 현재 유효한 확인을 모두 충족해야 한다. 실제 도구 경로로 해당 학습 확인을 마쳤으면 예시를 추가로 풀지 않는다. 결과만 기록하고 원리 학습이 남았다면 학습 확인을 안내한다. 유지·기능 생략도 그 분기의 필수 판단을 충족하면 실제 목표 확인이다. 공유 대체 과제는 미결이므로 대기 상태를 최종 완료로 올리지 않는다.

### 2. 실제 적용의 최소 상태 구조

자유 문장에서 ‘문제없음’ 같은 단어를 검색해 성공을 추정하지 않는다. 다음 의미를 명시적인 선택·확인으로 소유한다. 아래 식별자는 설계상 이름이며 구현 타입 확정은 아니다.

| 기록            | 최소 의미                                                                                                       |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| projectIdentity | 이번 방문의 같은 프로젝트 식별과 현재 폴더/대표 주소 연결. 경로 텍스트만으로 자동 판별하지 않음                 |
| learning        | 수업별 진행·원리 확인과 출처. 현재 완료 값을 학습 층으로 이관하고 실제 성공으로 승격하지 않음                   |
| stageDecision   | 3단원 개선/유지, 4단원 상세 보기 적용/생략·저장 적용/생략. 미선택은 별도                                        |
| checkpoint      | ‘미확인 / 해봄·목표 미충족 / 목표 확인’과 본인 근거. 확인한 기준 버전과 현재 버전이 다르면 ‘재확인 필요’를 파생 |
| obstacle        | 막힌 확인 항목과 짧은 이유. 계정·환경/파일·동작/접속/기기/공유/기타 구분. 목표 확인과 독립                      |
| notes           | 관찰·요청·결과·남은 문제·선택적 첨부. 기존 원문을 보존하며 선택 분기 전환으로 삭제하지 않음                     |
| changeBasis     | 기획/내용/화면/동작/저장/공개 주소별 변경 버전과 확인 항목의 의존 관계                                          |

‘목표 확인’은 해당 행동을 직접 수행하고 기대 결과를 충족했다고 본인이 명시했을 때만 기록한다. 문제 기록은 자유롭게 남길 수 있고, 목표 충족을 막는 문제가 있으면 해당 항목은 목표 미충족이다. 사소한 추가 개선 메모만 있다면 목표 결과 확인을 유지할 수 있다. 둘의 차이는 학습자가 선택하며 자동 문장 판독을 하지 않는다.

**단원 실제 상태 산출 우선순위:**

1. 현재 적용되는 필수 항목이 모두 유효하면 ‘목표 결과 확인’.
2. 예전에 확인했지만 현재 기준과 다른 필수 항목이 있으면 ‘재확인 필요’. 동시에 막힌 이유가 있으면 함께 표시.
3. 충족하지 못한 항목에 obstacle이 있으면 ‘확인 대기’와 이유.
4. 결정·메모·시도 중 하나라도 있으면 ‘진행 중’.
5. 없으면 ‘미진행’.

과거에 목표 확인을 마쳤다가 수정한 경우 기록과 확인 당시 결과를 남기되 현재 성공 집계에서 제외한다. 최종 완료도 파생 값이며 별도 완료 버튼 하나로 덮어쓰지 않는다. 과거 완료는 ‘이전 확인 기록’으로 볼 수 있지만 현재 상태는 재확인 필요다.

**개별 확인 조작:** ‘아직 안 함 / 해봤지만 목표 미충족 / 목표 결과를 확인함’을 해당 항목에서 고르고, 관련 행동·결과를 짧게 남긴다. 기존 결과 문장에 확인 근거가 있으면 재입력하지 않는다. 경로·주소는 맥락으로 사용하지만 자동 검사 근거로 보지 않는다. 공유는 실제 전달 여부와 부탁한 행동만 남기며 상대 정보·캡처는 요구하지 않는다.

### 4. 화면의 공통 구성과 왕복

단원 화면 상단에는 ‘학습 확인’과 ‘내 프로젝트’의 현재 상태를 서로 다른 줄로 보여준다. 진행률 하나로 합치지 않는다. 설명과 공통 예시를 먼저 읽고, 실제 적용 영역에서 같은 프로젝트의 결과를 이어받는다. 기존 페이지·단계 안에서 표현하고 예시 모드/실제 모드를 강제로 오가는 별도 과정을 만들지 않는 안이다.

| 조건             | 실제 적용 영역                                                        | 주요 행동                                              |
| ---------------- | --------------------------------------------------------------------- | ------------------------------------------------------ |
| 학습만 진행 중   | 예시 출처와 배울 원리. 실제 작업은 미진행                             | ‘학습 이어가기’                                        |
| 실제 준비 미충족 | 기존 기획·메모는 보존해 열람 가능. 무엇이 빠졌는지 한 가지 안내       | ‘첫 파일 확인으로’ 등 정확한 준비 단계                 |
| 실제 작업 중     | 분기 선택과 그 분기에 필요한 확인 항목만 펼침                         | ‘내 파일에서 확인하기’. 자동 외부 조작 아님            |
| 유지/생략 선택   | 판단 이유와 실제 확인만 표시. 사용하지 않는 구현 항목은 필수에서 제외 | ‘판단과 확인 결과 남기기’                              |
| 막힘             | 확인된 결과·막힌 단계·다음 확인 행동 표시                             | ‘확인 대기 내용 남기기’, 학습 계속/다른 독립 확인 가능 |
| 목표 결과 확인   | 해당 결과와 출처, 다음 단원 인계                                      | ‘다음 단원에서 이어가기’                               |
| 재확인 필요      | 기존 문장·마지막 결과와 변경 이유 표시. 영향받은 항목만 강조          | ‘바뀐 부분 다시 확인하기’                              |

단원 요약은 예시 학습·실제 결과를 구분하고 다음 행동 하나를 우선 보여준다. 실제 목표가 남았어도 학습 다음 단원으로 갈 수 있음을 명시한다. ‘내 프로젝트 다음 작업’과 ‘다음 학습’을 같은 완료 버튼으로 묶지 않는다.

최종 화면은 학습 확인, 실제 단원별 결과, 공개·접속·공유·재배포 확인을 별도 표시한다. 프로젝트 완료 전이면 가장 앞선 필수 준비 또는 현재 막힌 단계로 안내하되 독립 항목으로 이동할 수 있다. 3단원 유지·4단원 생략은 ‘정당한 판단’으로 요약하고 미적용 경고를 붙이지 않는다.

지도는 학습 진도와 학습 선행만 사용한다. 실제 결과를 보고 싶으면 별도 ‘내 프로젝트’ 요약에서 접근한다. 같은 방문의 재열람·지도 왕복·모드 전환은 기록과 입력 포커스의 맥락을 보존하고, 기록을 보러 왔다고 학습을 다시 풀게 하지 않는다. 기본 학습 완료와 연결된 수집/보상 정책은 변경하지 않는다.

### 5. 단원별 선행 조건

**설명·기록 재열람과 새 학습 해금, 실제 적용 준비를 구분**한다. 한 번 열린 학습은 기획 수정 때문에 다시 잠그지 않는 안이다. 학습의 핵심 답이나 분기를 수정하면 해당 확인은 재확인 필요로 표시할 수 있지만 이미 열린 뒤 단원을 닫지 않는다.

| 단계   | 새 학습 해금                                           | 실제 적용의 준비·판정 조건                                                                                                                                           |
| ------ | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 내부 | 기존 AI 이해→종류·도구→준비 설명→첫 대화→에이전트 순서 | 실제 도구 요청은 준비 확인 필요. 설명/예시 복습은 설치·로그인 성공과 분리                                                                                            |
| 2      | 1단원 다섯 수업의 학습 확인                            | 같은 프로젝트의 첫 파일이 실제로 존재하고 열 수 있어야 초안 목표 확인 가능. 부족하면 1단원의 필요한 항목으로 안내                                                    |
| 3      | 2단원 학습 확인                                        | 현재 기획과 맞는 실제 초안을 읽고 주요 행동을 확인한 상태. 부족해도 화면 설명·관찰 메모 열람 가능                                                                    |
| 4      | 3단원 학습 확인                                        | 같은 초안과 기획·주요 내용. 3단원 개선/유지 확인이 남아도 동작 필요 판단 메모 가능. 현재 두 화면·행동 확인이 충족돼야 단원 목표를 최종 유효로 집계                   |
| 5      | 4단원 학습 확인                                        | 공개 전 점검·배포에는 현재 파일·기획·기능 범위가 명확해야 함. 로컬 내용/화면/필요 동작의 핵심 문제는 먼저 안내. 초안·분기 결과가 달라졌다면 공개 전 점검 재확인 필요 |
| 최종   | 모든 설명·기록은 열린 상태로 재열람                    | 전체 학습과 현재 유효한 실제 목표, 공유·재배포 확인 모두 필요                                                                                                        |

실제 적용의 선행은 **설명·입력·독립 행동을 막는 잠금이 아니라 결과를 유효하게 집계할 준비**다. 예를 들어 3단원 재확인이 남아도 이미 수행한 5단원 공유 사실을 기록할 수 있지만 전체 프로젝트 완료는 보류한다. 앞 확인을 마쳤다고 뒤 결과를 자동 성공으로 바꾸지 않으며, 뒤에서 실제로 확인한 항목은 기록을 그대로 이어 쓴다.

학습 필수는 공통 원리 확인과 선택 경로에 맞는 정리다. 3단원 유지·4단원 생략 경로에서도 공통 원리를 설명하고 확인해야 하지만 실제로 필요 없는 수정/저장 조작은 강제하지 않는다. 기존 퀴즈는 목표 원리와 일치하면 유지하고 고정 예시의 불필요한 조작 횟수는 완료 근거로 쓰지 않는다.

### 6. 기록 수정 시 보존·재확인 규칙

**입력 중인 초안과 적용한 기준을 분리**한다. 타이핑할 때마다 후속 기록을 초기화하지 않는다. ‘변경 내용 적용’에서 기준이 바뀌는 범위를 보여주고 기록은 보존한 채 관련 확인만 재확인 필요로 바꾼다. 같은 내용으로 적용하거나 취소하면 상태를 바꾸지 않는다. 자동 원문 덮어쓰기·자동 외부 반영은 없다.

변경 범위는 **학습자의 명시적 선택**으로 기록한다. 워크북이 외부 파일을 감시하거나 AI로 차이를 추정하지 않는다. 한 변경이 여러 범주에 해당하면 재확인 범위를 합친다. 범위를 모르겠으면 현재 결과와 관련된 후속 항목을 넓게 재확인하되 원문은 지우지 않는다. ‘기록만 정정’은 실제 사이트·기획이 변하지 않은 경우에만 사용한다.

학습 원리 확인은 실제 기획·파일 변경으로 취소하지 않는다. 해당 학습 정리 자체에서 핵심 판단을 수정하면 그 원리 확인만 재확인하고 다른 학습 완료를 삭제하지 않는다. 이미 열린 학습은 유지한다.

**분기 왕복:** 적용→생략→적용으로 돌아오면 이전 적용 원문은 다시 보여주지만 예전 확인을 자동 복원하지 않는다. 새로 적용한 판단과 현재 파일을 대조해 해당 항목을 재확인한다. 숨긴 입력을 제출하거나 타 분기의 메모로 완료를 계산하지 않는다.

**의존 관계 처리:** 선행 확인이 재확인 필요가 되면 뒤 기록을 모두 초기화하지 않는다. 뒤 결과는 보존하되 ‘앞 단원의 현재 기준 확인 필요’를 표시하고 현재 유효 집계만 보류한다. 선행이 확인되면 뒤 항목 중 기준 자체가 변하지 않은 확인은 다시 유효해질 수 있다. 실제 내용·파일 변경으로 뒤 항목의 기준 버전도 바뀌었다면 그 항목은 별도 재확인해야 한다. 재확인 버튼 한 번으로 모든 뒤 항목을 일괄 성공 처리하지 않는다.

예: 소개문을 실제 파일에서 바꿨다면 과거 타인 공유 사실은 남고, 새 내용·두 화면·공개 자료·새 배포본 반영을 다시 확인한다. 같은 주소를 유지했으므로 상대에게 다시 보내거나 답장을 요구하지 않는다. 저장 코드가 그대로라면 단순 소개문 오타 수정 때문에 저장 과제를 다시 풀 필요는 없다.

### 7. 기존 기록 연결과 저장 수명

기존 completed/projectCompleted 등은 학습 층의 출처로 가져온다. 기존 practice의 컴퓨터 checks·applications.confirmed는 마지막 본인 기록으로 보존하되 새 목표 항목이 충분한지 대조한다. 명확히 대응하는 확인은 재사용하고, 공개·공유·재배포처럼 기존에 없던 항목은 미확인으로 둔다. 이전 ‘내 파일 4/4’만으로 새 프로젝트 완료를 만들지 않는다. 새로운 자기 확인을 예시 조작으로 채우지 않는다.

도메인 상태는 워크북 공통 context가 소유하고 진행·지도·요약은 같은 순수 판정에서 파생하는 구조를 제안한다. 화면별 별도 성공 boolean을 늘려 서로 다른 완료가 생기게 하지 않는다. 기존 lessonUi는 열린 설명·현재 단계 같은 UI 위치만 소유한다. 최종 타입·함수 이름은 구현 설계 승인 후 정한다.

**보존은 같은 방문에서의 수정·왕복 범위**다. 현재 진도·기획은 방문 메모리이며 새로고침/방문 종료 뒤 복원·회원 동기화를 새로 약속하지 않는다. 기존 브라우저 임시 첨부는 별개 자료로 보존하고 첨부 복원만으로 학습/현재 프로젝트 완료를 복원하지 않는다. 새 버전별 기록 저장소·서버·무한 변경 이력·프로젝트 목록을 만들지 않는다. 이전 결과 원문과 현재 기준의 연결만 유지한다.

### 후속 화면 연결에서 사용할 계약

`learn`은 원리 확인과 출처를, `note`는 메모를 기록한다. 실제 단원 메모에는 stage를 지정한다. 요청 초안·경로 표기 정정만으로 파일 변경을 추정하지 않는다. `decide`는 분기와 이유를 명시하고 해당 분기 확인의 버전을 갱신한다. 선택을 왕복해도 원문은 보존하지만 예전 성공은 자동 복원하지 않는다.

`change.values`에는 학습자가 적용했다고 지정한 변경 범주와 기준 값을 전달한다. 같은 값 재적용은 무시하고 여러 범주의 영향은 합쳐 항목당 한 번만 갱신한다. 파일 감시·자동 diff·AI 추정은 하지 않는다. 파일 내용을 보내거나 보관할 필요 없이 화면이 관리하는 명시적인 기준 값을 사용할 수 있다. 입력 중인 초안은 이 액션을 보내지 않고 ‘변경 내용 적용’에서만 보낸다.

`record`는 확인 항목·결과·근거와 현재 프로젝트 ID/항목 revision을 함께 받는다. 이전 버전이나 다른 프로젝트에서 늦게 들어온 확인은 무시한다. 근거 없는 성공 확인은 거절한다. ‘해봄·목표 미충족’과 마지막 성공 당시의 근거를 구분해 보존한다. 막힘은 항목별 `obstacle`로 기록하고 다른 독립 항목 확인을 막지 않는다.

`address`는 대표 주소 변경 시 접속·공유·공개 저장의 재확인을 요구한다. HTTPS/로컬/설명용 주소 등의 형태만 구분하며 실제 접속 여부를 검사하지 않는다. 같은 주소의 파일 갱신은 `change`의 deployment 범주를 사용해 과거 공유 사실을 유지한다. 새 프로젝트 지정은 모든 실제 확인을 재확인 상태로 바꾸되 기록과 학습을 보존한다. 다중 프로젝트 목록이나 영구 변경 이력은 만들지 않는다.

`stageProgress`는 필수 확인 중 누락된 항목, 미선택/이유 부족/주소 형태 같은 unresolved 사유, 선행 단원을 함께 반환한다. 뒤 결과를 기록할 수는 있어도 선행 목표가 유효하지 않으면 성공 집계는 보류한다. 선행만 바뀌었다면 원래 기준이 같은 뒤 확인을 다시 사용할 수 있고, 실제 파일 변경으로 항목 자체 revision이 달라졌다면 별도로 재확인해야 한다.

### 현재 화면과의 경계

상세 보기/저장 각각의 실제 확인·문제 대기와 생략 근거를 독립 체크포인트로 기록하고 두 화면·기존 주요 행동·저장 범위는 scope로 확인한다. 학습 원리와 판단을 정리하면 실제 문제를 성공으로 승격하지 않고 학습만 마칠 수 있다. 현재 브라우저의 선택이 다른 기기에 자동 동기화된다고 답하면 범위 확인을 기록할 수 없다. 기능 판단/파일 변경/확인 철회 시 이전 근거는 남고 새 실제 확인만 필요하다. 기준을 적용하지 않은 초안은 확인 근거와 섞이지 않으며 기존 단원 요약 호환 기록도 공통 체크포인트의 기록으로 구성한다. 앞 실제 단계가 남아도 독립 결과는 기록하고 목표 집계는 기존 순수 판정의 선행을 따른다.

4단원 요약·기록 이어하기·지도 안내를 연결했다. 4단원 학습 이력은 기록 편집/예시 전환만으로 취소하지 않는다. 기존 독립 완료 미리보기에 같은 4단원 수업을 여는 검수 버튼을 추가했다. 마지막 정리에서 4단원 확인을 수정했다면 다시 마지막 정리로 돌아갈 수 있다. 5단원 수업/배포 안내·실제 배포와 영구 진도·서버 연결은 변경하지 않았다. 전 단원의 최종 완료 화면을 새 판정으로 일괄 이관한 단계는 아니다.

### 4단원 검수·검증

자체 리뷰에서 두 기능의 독립 선택·생략 조건·기존 구현 확인·범위 원리·문제 대기·선행 조건·revision/원문 보존·초안과 적용 기준 구분·확인 철회·명시적 레이블과 키보드 이동을 대조했다. PC1440×900·모바일390×844의 실제 브라우저에서 상세 예시 열기/닫기, 상세 보기 생략과 독립 저장 적용, 입력·요청·실제 문제 대기를 확인했다. 이는 UI 상태와 본인 기록의 검수이며 외부 코드 에이전트의 실제 파일 제작·Windows/Mac 파일럿·실제 배포 검증은 아니다. 최종 검사 결과는 마감에 기록한다.

최종 `pnpm check` 타입·린트·포맷·29파일106테스트 통과(새 순수 분기5개 포함), 전체 E2E 203PASS·모바일 노트북 전용 1제외(6.7분). 네 조합의 PC·모바일8경로와 목적별 전체 연결6경로를 포함한다. 출력 `/tmp/workbook-unit4-final-20261021`, 디자인 증빙 `/tmp/workbook-unit4-design-20261021/{desktop,mobile}.png`. `git diff --check`와 후속 문서 포맷 확인도 통과했다. 초기 타입 인덱스 오류를 보정했고 연결 테스트의 기존 미적용/집계/기록 화면 전제를 새 4단원에 맞춰 수정한 뒤 최종 전체 실행을 통과했다. 초기 실패를 최종 통과에 합산하지 않는다. 검수 임시 탭·viewport·로컬 서버는 정리했으며 5단원 변경·외부 가입·실제 배포·커밋은 하지 않았다.

## 최신 변경 — 선택 절차 부분 롤백 · 2026-10-21

사용자의 후속 판단으로 과도한 적용/생략·생략 이유·새 실제 확인 절차를 초보의 기본 학습 진입/완료 조건에서 철회했다. 앞선 3·4단원 화면 구현 기록은 역사로 보존한다. 기본 화면 비교/메모 시뮬레이션을 복원하고, 상세 보기·자기 파일 세부 적용은 접힌 선택 읽기/실습으로 둔다. 선택 절차 없이 다음 학습으로 갈 수 있다. 기본 실습·기존 학습/첨부/적용 기록·무관한 버그 수정과 1·2단원 파일 연결은 보존했다. 5단원·실제 배포는 미변경이다.

공통 상태/기록 타입은 복구와 1·2단원 호환을 위해 남기며 3·4단원의 필수 판단 화면에서는 연결을 제거했다. 이전 추가 기록은 선택 영역에서 읽을 수 있다. 전체 UX 후속은 실제 화면 근거의 제안까지만 정리하며 구현하지 않는다. 백업/정확한 변경/검증/분석은 [부분 롤백과 UX 검수 기록](workbook-choice-rollback-and-ux-review.md)을 따른다.
