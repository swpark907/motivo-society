## goal에 넣을 문장 (복사용)

```text
docs/product/platform-review/GOAL.md 절차대로 플랫폼 디자인·사용성 검수를 진행해.
SCREENS.md의 모든 화면이 PC 1280·모바일 375에서 CHECKLIST.md 기준으로 검수 완료(✅)이고,
FINDINGS.md의 P0·P1이 전부 "고침(확인)" 또는 "결정 대기"이며,
pnpm check · pnpm test:db · 플랫폼 e2e(--workers=1)가 통과하면 끝이다.
```

## 목표

처음 온 사람과 호스트가 **실제 서비스처럼** 막힘없이 쓸 수 있는지 확인하고, 사람 결정 없이 고칠 수 있는 것은 고친다.

- 기준 1 — **사용성:** 어디 / 무엇을 / 그다음이 보이는가. 상태마다 맞는 문구인가. 빈·오류·기다림이 사람 말인가.
- 기준 2 — **디자인 일관성:** 플랫폼 제품 화면 예외(AGENTS.md)와 기준 시안(L01b, `/demo/design-platform/*`) 수준을 지키는가. 화면끼리 같은 것을 같게 보여 주는가.
- 기준 3 — **창의성과 절제:** 결과가 보이고 성취의 순간이 있는가, 움직임은 규칙(120ms · 색·불투명도) 안에서 하나 이하인가. 규칙을 넘는 아이디어는 FINDINGS "디자인 제안"에만 남긴다(CHECKLIST C).
- 기준 4 — **정직함:** 없는 기능·숫자·약속을 보여 주지 않는가(AGENTS 우선순위 1).

## 범위

- **포함:** `/` `/explore` `/activities/*` `/clubs*` `/invite/*` `/me*` `/host*` `/login` `/onboarding` `/learn`, 그리고 공통 GNB · 하단 탭 바 · 404 · 로딩.
- **경계만 본다:** `/learn`에서 워크북·Library·Article로 넘어가는 지점(넘어간 뒤의 워크북 화면 디자인은 범위 밖 — 워크북은 자체 규칙이 있다).
- **제외:** `/workbook/**` 내부, `/demo/**`(단, `/demo/design-platform/*`은 비교 기준으로 연다), 운영진 화면(시험장 `/demo/platform/ops`는 상태를 만들 때만 쓴다).

## 끝난 조건 (전부)

1. [SCREENS.md](SCREENS.md)의 모든 행이 PC·모바일 둘 다 ✅ (또는 이유 있는 ➖ 해당 없음).
2. [FINDINGS.md](FINDINGS.md)에 P0·P1이 남아 있지 않다 — 모두 `고침(확인)` 또는 `결정 대기`.
3. 여정 점검 J1~J4(CHECKLIST.md "여정")를 각각 한 번 끝까지 따라가 기록했다.
4. `pnpm check` · `pnpm test:db` · 플랫폼 e2e `--workers=1` 통과. 고친 화면에 맞춰 e2e를 고쳤으면 그 이유를 FINDINGS에.
5. FINDINGS.md 맨 위 "요약"에 고친 수 · 결정 대기 목록 · 남은 P2를 적었다.

## 한 번의 반복

goal이 여러 차례에 걸쳐 돌 수 있으므로, 상태는 이 폴더 파일과 git에만 둔다.

1. **상태 확인.** `git status`, FINDINGS.md 요약, SCREENS.md에서 첫 미완료 행.
2. **환경.** LOOP.md "환경 확인"과 같다. 요약:
   - `supabase status` → 꺼져 있으면 `supabase start`. 상태가 꼬였으면 `supabase db reset`(시드가 다시 들어간다).
   - 개발 서버: `http://localhost:3000`(승우) 우선, 없으면 브라우저 도구 `preview_start` 이름 `motivo-dev`(3100). 며칠 떠 있던 서버는 느리다 — 화면 하나가 10초를 넘으면 다시 띄울지 묻는다.
   - 로그인은 `/login`의 접힌 "개발용 · 시험장 사람으로 들어가기"에서 사람을 고른다(SCREENS.md의 사람 표).
3. **화면 하나(또는 같은 화면의 상태 묶음) 검수.**
   - PC 1280 → 모바일 375 순서로 연다. 모바일은 실제 뷰포트를 바꿔야 한다: 내장 브라우저 `resize_window {preset:"mobile"}` 또는 Playwright `viewport: {width:375,height:812}`. **Chrome 창 크기 조절은 최소 폭 때문에 375가 안 된다**(2026-11-10 확인: 390 요청 → 실제 1568).
   - [audit-snippet.js](audit-snippet.js)를 페이지에서 돌려 숫자를 먼저 얻고, 그다음 스크린샷으로 CHECKLIST의 눈으로 보는 항목을 본다.
   - 상태가 필요한 화면은 시험장으로 만든다(SCREENS.md "상태 만드는 법").
4. **기록.** 발견마다 FINDINGS.md에 한 행(ID · 화면 · 체크 ID · 심각도 · 무엇 · 근거). SCREENS.md 해당 칸 ✅.
5. **고치기.** 아래 "고쳐도 되는 것"이면 고치고 같은 화면을 다시 열어 확인 → `고침(확인)`. 아니면 `결정 대기: 누가 무엇을`.
6. **확인 묶음.** 고친 게 쌓이면 `pnpm check`와 해당 e2e. 화면 묶음(예: 호스트 전체)이 끝날 때마다 플랫폼 e2e 전체.

### 심각도

| 등급 | 뜻                                                                                             | 예                                                       |
| ---- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| P0   | 여정이 막힌다 · 잘못된 돈/상태를 보여 준다 · 데이터가 틀린다 · 가로 스크롤                     | 신청 버튼이 탭 바에 가림, 환불 금액이 화면마다 다름      |
| P1   | 할 수는 있지만 헷갈린다 · 상태 문구가 틀린다 · 정직함 위반 · 접근성 위반(이름 없음, 44px 미만) | "이번 주"에 3주 뒤 활동, 0개 카테고리를 문으로 보여 줌   |
| P2   | 다듬기 · 일관성 · 리듬                                                                         | 같은 카드가 한 화면에 세 번, 링크가 제목에서 멀리 떨어짐 |

### 고쳐도 되는 것 (사람 결정 없이)

- 문구가 상태와 어긋남, 같은 내용 반복, 빈 상태·오류 문구, 누름 영역, 포커스, 이름 없는 버튼, 여백·정렬·줄바꿈, 화면 사이 같은 요소의 불일치(배지 · 날짜 형식 · 가격 표기).
- 이미 정해진 규칙(AGENTS.md 디자인 · 플랫폼 제품 화면 예외 · L01b 원칙)을 지키도록 바로잡기.

## 하지 않는 것 (만나면 `결정 대기`로)

- IA(메뉴 · 경로) 바꾸기, 브랜드·디자인 규칙 바꾸기, 새 기능 추가, 새 의존성.
- DB 스키마 변경. 화면이 필요로 하는 데이터가 없으면 결정 대기.
- 가격 · 환불 규정 · 정산 주기의 실제 값, 성과·수익 약속 문구.
- 이미 결정 대기에 있는 것(BACKLOG "결정 대기")을 혼자 정하기 — 예: `--white` → 의미 토큰 전환, 참가자 얼굴 공개.
- `main` 머지 · `git push` · 원격 DB.
- **커밋:** 승우가 정한다. 정하기 전 기본값은 "커밋하지 않고 묶음마다 보고". (LOOP.md 예외처럼 `feat/platform-app`에 묶음 단위 커밋을 허용하면 이 줄을 고친다.)
