# 호스트의 비공개 클럽 · 초대 링크 · 실시간 채팅 · 호스트 시나리오 (2026-11-13)

승우와의 논의로 정한 것과 아직 정할 것을 한곳에 둔다. 수치·요금은 확인한 날짜(2026-11-13)의 공식 문서 기준이며 바뀔 수 있다.

## 1. 정한 것 (2026-11-13 승우 결정)

1. **그릇의 이름은 "클럽"이다.** 호스트가 운영하는 그룹 = 클럽. 그 안에 한 번씩 열리는 것 = 모임·시즌·챌린지(활동). 새 개념을 만들지 않고 지금의 클럽을 넓힌다.
2. **호스트의 클럽은 기본 비공개(목록에 안 뜸)다.** 둘러보기·홈·클럽 목록에는 **모쏘가 직접 연 클럽과 활동만** 나온다. 호스트 클럽과 그 안의 활동은 링크를 가진 사람만 본다. 검색엔진 수집도 막는다.
3. **초대는 링크를 공유하는 방식이다.** 기본은 여러 사람이 같이 쓰는 링크 하나이고, **가입 승인제를 기본으로 켠다.** 링크는 문이고, 문지기는 승인이다.
4. **실시간 채팅을 직접 만든다.** 커뮤니티 기획(`platform-community-plan.md`)의 "상주형 실시간 채팅은 웹 단계에서 직접 만들지 않는다"는 결정을 바꾼다. 구현 방식은 4절.

## 2. 공개 단계

| 단계      | 목록·검색 노출 | 링크로 들어온 사람이 보는 것  | 누가 쓰나                 |
| --------- | -------------- | ----------------------------- | ------------------------- |
| 공개      | 보임           | 호스트가 연 섹션 전부         | 모쏘가 연 공식 클럽(지금) |
| 링크 공개 | 안 보임        | 소개·규칙 + 호스트가 연 섹션  | **호스트 클럽 기본값**    |
| 초대 전용 | 안 보임        | 소개·규칙만, 나머지는 승인 뒤 | 민감한 소규모 클럽(선택)  |

링크로 들어온 화면은 그 자체로 완결되어야 한다(무엇인지, 누가 여는지, 어떻게 들어가는지). 카톡·인스타 DM 미리보기(OG)는 링크 공개 클럽에도 만든다.

## 3. 초대 링크

**기본: 공용 링크 + 승인제.** 사람마다 만드는 1회용 링크는 호스트가 귀찮아 쓰지 않는다. 대신 공용 링크에 안전장치를 둔다.

- **새로 만들기 = 이전 링크 끄기.** 유출됐다 싶으면 바로 막는다.
- **기간·인원 제한.** "이번 주까지 · 20명까지".
- **이름 붙인 여러 링크.** "인스타용", "1기 단톡방용"처럼 나눠 어디서 왔는지 보고 하나만 끌 수 있다.
- **승인제와 함께.** 링크로 들어와도 호스트가 확인해야 멤버가 된다(기본 켬). 가입 질문 한두 개로 판단 근거를 받는다.

**호스트 자격은 링크로 주지 않는다.** 운영진이 관리 화면에서 켠다(6-2절).

**지금 구현과의 차이:** `club_invites`에 코드·만료·최대 횟수·사용 수·폐기 열이 있고(`club_invite_create`는 7일 만료 고정), `/invite/[code]` 미리보기와 가입이 있다. 다만 **지금은 초대 링크로 들어오면 승인제 클럽이어도 바로 멤버가 된다**(slice9). 결정 3에 맞춰 바꿔야 한다. 링크 이름·기간 선택·끄기 화면도 아직 없다.

## 4. 클럽 안의 섹션과 공개 설정

| 섹션                 | 구성원이 아닌 사람에게 (확정 기본값) | 이유                              |
| -------------------- | ------------------------------------ | --------------------------------- |
| 소개·규칙            | 항상 보임(고정)                      | 링크로 온 사람이 뭔지 알아야 한다 |
| 열린 모임            | 보임 · 끌 수 있음                    | 들어올 이유                       |
| 지난 기록(후기·사진) | 보임 · 끌 수 있음                    | 들어올까 망설이는 사람의 근거     |
| 게시판(공지 / 자유)  | 숨김 · 켤 수 있음                    | 안에서 편하게 말하는 곳           |
| 구성원               | 숨김 · 켤 수 있음                    | 개인정보                          |
| 채팅                 | 항상 숨김(고정)                      | 스팸·개인정보                     |

"구성원이 아닌 사람"에는 로그인하지 않은 사람과 모쏘 회원이지만 이 클럽 멤버가 아닌 사람이 함께 들어간다. 호스트는 섹션마다 이 한 가지만 고른다. **이 표의 기본값은 2026-11-13 승우가 확정했다.** 들어올지 판단하는 데 필요한 것(소개·열린 모임·지난 기록)은 보이고, 안에서 오가는 것(게시판·구성원·채팅)은 숨긴다. 운영진은 설정과 관계없이 모든 섹션을 볼 수 있다(약관 고지).

추가로 권하는 섹션: 소개·규칙(필수), 지난 기록, 가입 질문, (나중에) 결과물·링크 모음.

## 5. 실시간 채팅 — Supabase로 가능한가

**가능하다.** Supabase Realtime의 Broadcast + 비공개 채널(RLS 권한)로 클럽별 채팅방을 만들 수 있다. 이미 쓰고 있는 Supabase(DB·로그인)와 같은 계정·권한 체계라 별도 서비스가 필요 없다. 이 레포의 `@supabase/supabase-js`는 2.118.0이다.

### 5-1. 구조(제안)

- **정본은 우리 테이블.** `club_messages`(클럽·보낸 사람·본문·작성 시각·삭제 시각)에 저장하고 RLS로 "그 클럽의 활성 멤버만 읽기/쓰기". 지난 대화는 이 테이블에서 페이지로 불러온다. Realtime의 다시 보기(replay)는 72시간까지만이라 기록 보관용이 아니다.
- **실시간 알림만 Broadcast로.** 메시지가 저장되면 DB에서 클럽별 비공개 채널(`club:<id>`)로 **새 메시지의 id만** 보낸다. 받은 화면은 id로 본문을 테이블에서 읽는다(RLS가 다시 확인).
  - 이유: 비공개 채널 권한은 **접속할 때 확인하고 그 연결 동안 유지된다.** 강퇴된 사람이 로그인 토큰이 끝날 때까지 방송을 받을 수 있으므로, 방송에 본문을 싣지 않는다.
- **비공개 채널 권한**은 `realtime.messages`에 RLS 정책을 두고("Allow public access" 끔), 클라이언트는 `private: true`로 구독한다.
- **읽음 위치**(`club_message_reads`: 멤버별 마지막으로 읽은 시각)로 안 읽은 수를 보여 준다.
- **운영 장치(처음부터):** 글자 수 제한, 보내기 속도 제한(RPC에서), 본인·호스트 삭제, 신고, 강퇴(`club_ban`이 이미 있다)와 연동.

### 5-2. 요금제 · 한도 (공식 문서, 2026-11-13 확인)

| 항목               | Free                    | Pro                                                    |
| ------------------ | ----------------------- | ------------------------------------------------------ |
| 월 요금            | $0                      | $25부터(조직 단위, 컴퓨트 $10 크레딧 포함 = Micro 1개) |
| 비활성 시 정지     | **1주 비활성이면 정지** | 정지 없음                                              |
| DB / MAU / 전송량  | 500MB / 5만 / 5GB       | 8GB / 10만 / 250GB                                     |
| Realtime 동시 연결 | 200                     | 500 (지출 상한을 끄면 10,000)                          |
| Realtime 메시지    | 월 200만                | 월 500만, 넘으면 100만당 $2.50                         |
| 초당 메시지        | 100                     | 500 (지출 상한을 끄면 2,500)                           |
| 연결 초과 요금     | —                       | 최고 동시 연결 1,000당 $10                             |

메시지 세는 법: Broadcast 하나를 4명이 받으면 **보낸 것 1 + 받은 것 4 = 5개**로 센다.

**운영은 Pro가 필요하다.** 채팅 때문이 아니라 Free는 1주 비활성이면 정지되어 서비스에 쓸 수 없다. Pro의 동시 연결 500은 **지출 상한을 켠 상태의 상한**이라 넘으면 접속이 거절된다. 사람이 늘면 지출 상한을 끄고 사용량만큼 낸다.

### 5-3. 대략의 비용 추정 (가정이 들어간 계산)

가정: 클럽 하나가 하루 150개 메시지, 보낼 때 평균 4명이 화면을 열어 둠(1개당 5개로 셈) → 클럽당 하루 750개, 월 약 2.25만 개.

| 규모         | 월 Realtime 메시지 | 추가 비용(Pro 기준)      |
| ------------ | ------------------ | ------------------------ |
| 클럽 10개    | 약 23만            | 0 (포함량 안)            |
| 클럽 100개   | 약 225만           | 0 (포함량 안)            |
| 클럽 1,000개 | 약 2,250만         | 넘는 1,750만 → 약 $45/월 |

동시 연결은 **채팅 화면을 연 동안만 구독**하면 작게 유지된다(모든 화면에서 구독하면 접속한 사람 수만큼 연결이 생긴다). 초기 규모에서는 채팅이 Pro 기본 요금 위에 거의 비용을 더하지 않는다.

### 5-4. 가장 큰 위험 — 알림

Supabase에는 휴대폰 푸시가 없다. **알림이 없으면 사람들은 단톡방으로 돌아간다.**

**결정(2026-11-13 승우): 지금은 사이트 안 숫자 + 웹 푸시까지, 나중에 앱 푸시.** 이메일 알림은 지금 만들지 않는다.

1. 사이트 안: 상단 메뉴와 클럽 카드에 안 읽은 수.
2. **웹 푸시:** 웹을 설치형 웹앱(PWA: 매니페스트 + 서비스 워커)으로 만들고, 브라우저 푸시(Web Push · VAPID 키)로 보낸다. 구독 정보는 DB에, 보내기는 서버(Next.js 서버 또는 Supabase Edge Function)에서. PC·안드로이드는 바로 받고, **iOS는 홈 화면에 추가한 웹앱(16.4 이상)에서만** 받는다 — 그래서 "홈 화면에 추가" 안내가 함께 필요하다.
3. 앱 단계: 앱 푸시(앱 확장 전략에서 정한다).

알림 받을 일(제안): 채팅에서 나를 부름 · 클럽 공지 · 가입 신청(호스트)과 승인 결과(신청자) · 모임 하루 전·시작 전 · 입금 확인. 사람마다 켜고 끌 수 있게 한다.

### 5-5. 플랜 관련 열린 것

- 운영 Supabase는 대표의 motivo.kr 프로젝트를 같이 쓴다(2026-11-13 결정). 그 프로젝트의 요금제(Free/Pro)를 확인해야 한다 — Free면 채팅 한도와 1주 비활성 정지가 걸린다. 흡수 순서는 `docs/architecture/landing-absorption-plan.md`.

## 6. 호스트 시나리오 — 소개부터 첫 멤버 가입까지

### 6-1. 소개 (밖에서)

- **누구에게:** 이미 카톡 단톡방·소모임 앱·인스타로 모임을 굴리는 사람. 특히 바이브코딩·AI·만들기 모임.
- **어떻게:** 초기에는 모쏘 운영진이 직접 연락한다(공개 모집 전). 보여 줄 것은 두 가지다.
  - 호스트 소개 화면(예: `/hosting`): 지금 실제로 되는 것만 적는다. 신청·입금 확인·명단·출석·공지·장부·정산(H01~H11 구현 완료), 비공개 클럽과 초대 링크, 채팅·게시판(구현 후). 아직 안 되는 것(카드 결제, 앱 알림)은 안 된다고 쓴다.
  - 시험장 데모 계정으로 직접 눌러 보는 시연.
- **수수료·정산 조건**은 아직 미결이다. 소개에서 약속하지 않는다(대표 승인 사항).

### 6-2. 가입과 호스트 자격

**원칙(2026-11-13 승우 결정): 호스트는 전부 들어오기 전에 거른다.** 모쏘의 약속은 "깨끗하고 영양가 있는 모임과 클럽"이고, 신고·제재는 이미 누군가 나쁜 경험을 한 뒤의 사후 처리다. 그래서 "가입하면 누구나 무료 클럽을 열고 돈 받기만 심사"하는 단계별 자격안은 쓰지 않는다. 이 관문은 AGENTS.md의 "열림"(누구나 **읽을** 수 있다)과 충돌하지 않는다 — 여는 사람을 고르는 일은 판단 기준 1번(신뢰)에 속한다.

호스트는 계정 종류가 아니라 자격이다(기존 결정). 단계:

- **초기(운영진이 직접 섭외):** 호스트는 일반 회원으로 가입하고, **운영진이 관리 화면에서 그 회원에게 호스트 자격을 켠다**(2026-11-13 승우 결정). 1회용 호스트 초대 링크는 쓰지 않는다 — 일반 가입 흐름을 그대로 쓰고 만들 화면이 적다. 자격을 켜면 호스트에게 "이제 클럽을 열 수 있어요" 안내가 보이고, 그 자리에서 가이드라인 동의를 받는다.
- **공개 모집:** 회원 누구나 "호스트 신청"(하려는 클럽 · 운영 경험 · 지금 굴리는 모임 링크) → 운영진 심사 → 승인. 심사 기준은 미결.
- **승인할 때 받는 것:** 호스트 가이드라인 동의(모쏘다운 모임의 기준 · 금지 사항 · 운영진 열람 고지).

**승인 뒤의 사전 관리(사후 처리만으로 두지 않는다):**

- 새 호스트의 첫 한두 번 모임은 운영진이 공지·소개를 미리 보거나 직접 참석한다.
- 끝난 모임마다 참가자에게 짧은 후기를 받아 운영진이 본다(공개 별점이 아님).
- 운영진(소유자 역할)은 목록에 안 뜨는 비공개 클럽도 안을 볼 수 있다. 이 사실은 이용약관·호스트 가이드라인에 밝힌다.
- 신고·제재(정지·자격 회수)는 그 위에 남는 마지막 장치다.

### 6-3. 클럽 만들기

`/host` → "클럽 만들기" 한 화면(또는 짧은 단계):

1. 이름 · 한 줄 소개 · 주소(영문, 바꾸지 않는 영구 주소)
2. 소개와 규칙
3. 가입 방식: **승인제(기본)** / 바로 가입. 승인제면 가입 질문 1~2개
4. 섹션 공개 설정(4절 기본값 그대로 두고 바꿀 수 있음)
5. 만들면 **링크 공개** 상태로 생긴다. 관리자·운영진·멤버 레이어가 함께 생긴다(지금의 `club_create`).

### 6-4. 멤버 초대와 가입

1. 호스트: 클럽 화면 → "초대 링크 만들기" → 이름(예: 1기 단톡방) · 기간 · 인원 → 링크 복사.
2. 호스트가 단톡방·DM에 붙여 넣는다. 미리보기에 클럽 이름·소개가 보인다.
3. 받은 사람: 링크를 열면 소개·규칙과 호스트가 연 섹션이 보인다 → "가입 신청".
4. 로그인·가입(매직링크) → 첫 가입이면 짧은 온보딩 → **같은 초대 화면으로 돌아온다** → 가입 질문 답 → "승인을 기다리고 있어요".
5. 호스트: 승인 대기 목록에서 승인/거절(지금 `club_member_decide`). 알림은 5-4절 단계를 따른다.
6. 승인된 멤버: 클럽 홈에서 채팅·게시판·열린 모임이 열린다. 첫 진입에 환영 공지(호스트가 미리 적어 둔 문구, 호스트 보관함과 연결).

예외 흐름: 이미 멤버 → 클럽으로 바로. 강퇴된 사람 → 초대로도 못 들어옴(지금 구현됨). 만료·꺼진 링크 → "호스트에게 새 링크를 받아 주세요".

### 6-5. 첫 모임 열기

클럽 안에서 "모임 만들기" → 클럽 활동으로 생성. 클럽이 링크 공개면 그 활동도 둘러보기에 안 뜨고, 클럽 멤버에게 공지·채팅으로 알린다.
