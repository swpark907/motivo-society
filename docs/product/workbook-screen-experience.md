# 화면과 사용 경험 · 첫 화면의 넘침 고치기

4+1 구조의 ‘화면과 사용 경험’ 첫 단위다. 앞 단원의 홈페이지 제목·독자·목적·소개·내용을 그대로 사용한다. 별도 지도 원화는 아직 준비 중이며, 첫 맵 완료 기록 아래 다음 단원 버튼으로 연결한다.

- 선행 조건: AI 입문 다섯 수업과 ‘내 홈페이지 기획하고 만들기’ 완료. 기획 미리보기 복습 완료로도 이어갈 수 있으나 실제 파일 수정과 구분한다.
- 학습 결과: 같은 소개 페이지를 휴대폰 280px·넓은 화면 560px에서 보고, 제목·목록·버튼이 작은 화면 밖으로 나가는 한 문제를 기록한다. index.html의 고정 너비 한 부분만 개선하도록 요청하고 두 화면의 전후를 비교한다.
- 흐름: 두 화면 관찰 → 구체적 요청 작성 → 화면에 맞는 너비 적용과 전후 비교. 기존 모바일 소개 페이지 실험의 CSS 미리보기 컴포넌트를 재사용한다. 또 다른 지도나 별개 실험을 추가하지 않는다.
- 완료 기준: 두 크기에서 수정 전 확인, 관찰 기록과 요청, 수정 적용 후 두 크기와 ‘내용 보기’ 버튼 확인, 비교 기록. 체크는 예제 화면의 조작 확인이며 외부 코드 에이전트 실행을 자동 검증하지 않는다.
- 기록: 방문 중 메모리. 지도·이야기·목록 왕복 유지, 새로고침 초기화. 첫 제작 기록을 바꾸면 이 단원의 관찰·비교도 초기화해 다른 페이지의 기록이 섞이지 않게 한다.

필수 개념은 본문에서 설명한다. ‘반응형’은 같은 내용이 화면 너비에 맞게 배치되는 것으로, 여기서는 고정 너비를 화면에 맞는 너비로 바꾸는 한 가지를 경험한다. 실제 파일에 적용할 때는 요청을 외부 앱에서 실행하고 PC·모바일에서 다시 확인한다. 이번 단원은 레포 안 CSS 예시 비교 복습이며 실제 파일 수정 완료로 표시하지 않는다.

## 2026-10-10 최소 입문 안내 보완

280px/560px은 연습 화면 조건이라는 점을 초안 옆에 표시하고 실제 파일에는 직접 확인한 문제·화면 크기로 바꾸도록 안내했다. 같은 문제가 없는 파일에 넘침 결함이 있다고 전제하지 않도록 명시했다. 기존 코드 용어 펼치기에 HTML 구조/CSS 너비·색/JavaScript 메모 표시와 HTML 링크 이동 예외를 연결했다. 문구·기존details본문만 수정했고 생성요청·input·선행·완료·라우팅은 그대로다. 최소 포맷·정적대조만 확인하며 실제Windows/Mac 신규설치/외부배포파일럿은 미검증이다.

## 2026-10-15 · 입문자의 예시/내 파일 구분

세 활동마다 `WorkbookPracticeScope`로 워크북에서 할 조작을 먼저 보여주고, 내 파일에 적용할 때의 차이는 펼쳐보기로 제공한다. 단원 제목과 지도 기록의 시작 버튼을 ‘작은 화면에서 예시 페이지 확인하기’로 맞췄다. 입력은 ‘예시의 작은 화면에서 불편한 한 가지’·‘연습 화면의 개선 요청’·‘예시 수정 전후 달라진 점’으로 구분한다. 연습의280/560px조건을 내 파일의 문제로 가정하지 않으며 실제 같은 문제가 없으면 같은 수정을 요구하지 않는다. 실제 적용은 마지막의 ‘내 프로젝트 적용 기록 · 선택’에서 요청 복사→AI 앱→파일 재확인으로 이어진다. 기존 실험/완료 조건은 유지한다.

## 자기 초안의 관찰·개선·유지 판단 보강 원고 — 2026-10-20

승인된 프로젝트 연계 기준에 따른 3단원 후속 원고다. 위 280px/560px 넘침 예시와 필수 조작은 현재 구현 이력으로 보존한다. 아래는 같은 자기 초안을 중심으로 바꾸는 목표 원고이며 수업 코드·화면·완료 판정·저장 구조에는 아직 적용하지 않는다. 고정 오류 예시는 관찰 연습에 활용하되 자기 파일에 같은 오류가 있다고 가정하지 않는다.

### 도입 — 같은 초안을 두 화면에서 읽어봐요

앞 단원에서 내 콘텐츠를 담은 첫 초안을 만들었어요. 이번에는 **같은 프로젝트의 같은 파일**을 처음 방문한 사람처럼 살펴볼 거예요. 새 페이지를 만들거나 기획을 다시 쓰지 않아요.

내가 무엇을 말하려는지 알고 읽을 때와 처음 보는 사람이 읽을 때는 다를 수 있어요. 제목부터 내용을 따라가고 주요 버튼을 눌러보면서, 읽거나 행동하는 데 걸리는 부분을 찾아요. **필요한 부분은 고치고, 충분히 괜찮은 부분은 이유를 남겨 유지**해요.

실제 파일이 아직 없다면 앞 단원의 첫 초안 만들기부터 이어가요. 예시로 복습할 수도 있지만, 예시를 조작한 결과가 자기 파일을 고친 결과가 되지는 않아요.

### 활동 1 — PC와 모바일 폭에서 확인해요

**무엇을 보고 있는지부터 확인**

`my-first-web`의 초안 파일을 브라우저로 열어요. 앞 단원의 제목·소개·주요 내용이 맞는지 확인해요. 화면이 다르다면 새 예제를 만들지 말고, 에이전트가 바꾼 파일과 브라우저에서 연 파일의 위치를 먼저 맞춰요.

**넓은 화면에서 시작**

PC 화면에서 제목→소개→주요 내용→다음 행동을 따라 읽어요. 처음 보는 사람이 페이지의 목적을 알 수 있는지, 관심 내용을 찾을 수 있는지 살펴봐요. 버튼이나 링크는 실제로 눌러 도착 결과를 확인해요.

**같은 내용을 좁은 화면에서 확인**

컴퓨터의 브라우저 창을 휴대폰 화면처럼 좁혀 같은 순서로 읽어요. 좁은 창만으로 폭을 확인하기 어렵다면 브라우저의 기기 미리보기 기능을 보조로 사용할 수 있어요. 사용하는 브라우저의 정확한 조작은 실습 안내에서 별도로 확인해요.

‘반응형’은 **같은 내용이 화면 너비에 맞춰 배치되는 것**이에요. PC용·모바일용 사이트를 각각 새로 만들라는 뜻이 아니에요. 창을 좁혀 보는 것은 배치 확인이고 실제 휴대폰의 터치·키보드·브라우저 전체 환경을 검사한 것은 아니에요. 다른 기기의 공개 접속은 5단원에서 별도로 확인해요.

| 살펴볼 것      | 스스로 해볼 확인                            | 개선이 필요할 수 있는 관찰                                  |
| -------------- | ------------------------------------------- | ----------------------------------------------------------- |
| 정보 순서      | 제목과 소개를 읽고 페이지 목적을 말해보기   | 장식이나 긴 문구 때문에 제공 내용이 한참 뒤에 나옴          |
| 글 읽기        | 소개와 중요한 설명을 처음부터 끝까지 읽기   | 글이 너무 작거나 줄이 지나치게 길고, 배경과 구별하기 어려움 |
| 간격과 구분    | 제목·본문·항목의 관계를 따라가기            | 서로 다른 항목이 붙어 보여 어디까지 한 내용인지 헷갈림      |
| 작은 화면 배치 | 문장·이미지·버튼 끝까지 보기                | 내용이 잘리거나 가로로 밀려 중요한 부분을 놓침              |
| 주요 행동      | 찾으려는 항목과 버튼을 찾아 실제로 눌러보기 | 버튼 문구로 도착지를 예상하기 어렵거나 다른 요소에 가려짐   |

표는 점검 기준이다. 모든 항목에서 문제를 만들어 적거나 정해진 수의 결함을 찾을 필요는 없다. 화면 크기에 따라 줄바꿈이 달라지는 것은 자연스러운 변화다. 읽기·내용 찾기·행동에 지장이 있는지로 판단한다. 예시의 280px/560px을 모든 실제 페이지의 고정 통과 폭으로 사용하지 않는다.

**관찰을 남겨요**

문제가 있다면 **어느 화면에서, 어디가, 어떤 행동을 어렵게 했는지** 적어요.

> 좁은 화면에서 작업 제목이 두 줄로 바뀌면서 아래 설명과 붙어 보여요. 어떤 설명이 어느 작업에 속하는지 구별하기 어려워요.

‘이상해요’나 ‘예쁘게 해줘’보다 확인한 상황을 알려줘요. 먼저 중요한 한두 곳을 고르고, 그 부분을 고쳤을 때 방문자가 무엇을 더 쉽게 할 수 있을지 생각해요.

### 활동 2 — 필요한 부분을 고치거나 유지해요

#### 개선이 필요한 경우

앞 관찰을 그대로 사용해 수정 요청을 만들어요. **바꿀 부분·원하는 결과·유지할 부분·확인할 화면**을 포함해요.

> 현재 my-first-web의 index.html을 먼저 읽고 같은 페이지를 수정해줘. 좁은 화면에서 작업 제목과 설명이 붙어 보여 항목 구분이 어려워. 항목 안의 제목·설명 관계는 유지하면서 서로 다른 작업 사이를 구분해줘. 제목·소개·작업 내용·기존 링크 목적지는 바꾸지 마. 넓은 화면에서도 구분이 자연스러운지 확인할 방법을 알려줘. 다른 파일 변경이 필요하면 이유와 범위를 먼저 알려주고, 설치·외부 서비스·배포는 하지 마.

이는 **간격 문제를 실제로 관찰했을 때의 요청 예시**다. 자기 파일의 관찰과 다르면 해당 부분을 바꾼다. 파일이 CSS·이미지 등으로 나뉘어 있다면 같은 프로젝트의 실제 구조를 알려준다. `index.html`에 모두 합치거나 새 폴더로 옮기게 하지 않는다. 더 넓은 파일 변경이 필요하면 이유와 범위를 읽고 판단한다.

에이전트가 수정한 뒤 어떤 파일이 바뀌었는지 확인해요. 완료 문장만 읽고 끝내지 말고 브라우저의 같은 초안을 새로고침해요. 기획·본문까지 바뀌었다면 요청한 유지 범위와 대조해 다시 수정해요.

#### 문제가 보이지 않거나 변경이 불필요한 경우

오류가 없으면 일부러 만들거나 전체 디자인을 다시 바꿀 필요는 없어요. **확인한 기준과 현재 화면이 충분한 이유**를 남겨요. 이 경우 수정 요청과 수정 전후 캡처를 억지로 만들지 않아요.

> PC와 좁은 화면에서 제목과 소개를 읽고 페이지 목적을 알 수 있었어요. 작업 설명이 잘리지 않고 각 항목도 구분돼요. 주요 링크가 의도한 작업으로 열려서 이번에는 배치를 유지해요.

‘마음에 들어요’만 적기보다 실제로 확인한 읽기·탐색·동작을 근거로 설명한다. 이 문장은 예시이며 확인하지 않은 항목을 그대로 제출하게 하지 않는다. PC만 봤다면 모바일 폭 확인은 남은 작업이다. 판단이 어렵다면 중요한 본문과 주요 행동부터 다시 확인하고 무엇이 헷갈리는지 좁힌다.

### 활동 3 — 같은 조건에서 결과를 다시 확인해요

**수정했다면** 처음 살펴본 넓은 화면과 좁은 화면에서 다시 읽어요. 브라우저 확대 비율과 창 너비 등 비교에 영향을 주는 조건은 가능한 한 같게 맞춰요. 무엇이 나아졌고 다른 부분에 새 불편이 생기지 않았는지 살펴봐요.

1. 관찰했던 부분에서 읽기나 항목 찾기가 실제로 쉬워졌나요?
2. 제목·소개·실제 내용과 유지하기로 한 부분이 남아 있나요?
3. 기존 주요 링크·버튼은 여전히 의도한 결과로 이어지나요?

수정 전 화면을 남기고 싶으면 캡처를 보조로 사용할 수 있어요. 캡처가 없더라도 처음 관찰한 문장과 현재 화면을 대조해요. 모든 단원에 전후 이미지나 영역 표시를 제출할 필요는 없어요.

**유지했다면** 앞에서 확인한 두 화면의 결과와 유지 이유를 최종 정리에 가져와요. 별도 수정 요청·가짜 전후 비교·반복 입력은 요구하지 않아요. 최종 정리 전 파일이나 기획을 바꿨다면 영향을 받은 내용·화면·주요 행동을 다시 확인해요.

| 결과                   | 짧게 남길 기록                                     | 인정하는 범위                                                       |
| ---------------------- | -------------------------------------------------- | ------------------------------------------------------------------- |
| 필요한 개선을 확인     | 관찰→변경 내용→두 화면의 결과와 기존 행동 확인     | 자기 파일의 화면 개선·확인                                          |
| 현재 화면을 유지       | 두 화면에서 확인한 기준→충분한 이유→주요 행동 확인 | 근거 있는 유지 판단·확인. 수정이 없다는 이유로 미완료 처리하지 않음 |
| 수정했으나 문제가 남음 | 확인된 변화와 미해결 부분, 다음 확인 행동          | 시도·부분 진행 기록. 목표 결과 확인으로 표시하지 않음               |
| 예시에서만 관찰·비교   | 예시에서 익힌 원리와 관찰                          | 학습 확인. 자기 파일 적용과 구분                                    |

실제 파일 결과는 본인 확인이다. 입력·캡처·에이전트의 완료 문장만으로 자동 검사나 성공 인증을 했다고 표현하지 않는다. 확인하지 못한 환경이나 행동은 남은 작업으로 남긴다.

### 단원 마무리 — 다음에는 필요한 동작을 판단해요

두 화면에서 읽고 행동해보며 **왜 고쳤는지 또는 왜 유지했는지** 설명할 수 있게 됐어요. 다음 단원에서는 같은 페이지에서 항목을 골라 자세히 볼 필요가 있는지, 선택을 나중에도 남길 필요가 있는지 살펴봐요.

4단원으로 넘길 것은 같은 프로젝트의 현재 파일·기존 기획과 실제 내용·주요 행동·관찰 및 개선/유지 판단·남은 문제다. 기획과 확인 결과는 기존 기록을 이어 사용하고 같은 설명을 다시 작성하게 하지 않는다. 기존 방문 메모리·새로고침 초기화 정책은 유지하며 원고 보강으로 회원 진도 저장을 약속하지 않는다.
