# 바이브코딩 워크북 상세 기획안

작성일: 2026-10-02 · 상태: 논의용 초안 · 검토자: 승우

2026-10-18 웹 클래스의 최신 프로젝트 연계 방향은 [1~5단원 커리큘럼과 개편 계획](workbook-web-class-project-curriculum.md)을 따른다. 아래 초기 확장 제안은 이력으로 보존하며 전체 항목의 구현 승인을 뜻하지 않는다.

기존 `vibe-web-class-ssot`의 웹개발 기초 수업을, AI와 함께 만들고 결과를 판단·수정하는 인터랙티브 워크북으로 전환하는 제안이다. 핵심은 교재를 화면으로 옮기는 데 그치지 않고, 참여자가 실제 제작 상황에서 선택하고 결과를 확인하며 자기 프로젝트를 개선하도록 만드는 것이다.

이번 문서는 콘텐츠와 경험의 상세 설계다. 개발 착수, 서비스 공개, 회원·진도 저장·AI 호출·주간 추천 기능의 구현을 확정하지 않는다. 책상 정리 데모는 현재 상태에서 대기하며, 정식 과정 채택 여부는 별도로 판단한다.

## 1. 확정된 방향과 이번 기획의 가정

| 구분               | 내용                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| 합의된 철학        | AI를 활용해 원하는 결과물을 만들고, 판단하고 개선하는 힘을 기른다.                                          |
| 합의된 경험        | 설명보다 직접 경험을 앞세운다. 투두·해빗 트래커와 진행률은 중심이 아니다.                                   |
| 합의된 확장        | 디자인·글쓰기 등으로 확장해도 AI와 함께 만드는 활동으로 이어진다. 모든 조작에 AI 호출이 필요한 것은 아니다. |
| 기존 클래스의 기준 | 겪을 상황 → 도움이 되는 원리 → AI에게 요청할 말 → 내가 판단·확인할 것.                                      |
| 대상 가정          | 오프라인 수업 없이 시작하는 입문자도 이용할 수 있게 설계한다. 아직 사용자 결정 전이다.                      |
| 첫 제작 제안       | 소개 페이지를 만들고 개선하는 짧은 과정을 먼저 검증한다. 전체 커리큘럼을 한 번에 구현하지 않는다.           |
| 도구 사용 제안     | 워크북 내부는 통제된 실험, 실제 제작은 사용자가 선택한 외부 AI 도구에서 진행한다.                           |
| 문서의 수치        | 활동 시간·사용성 검증 인원은 계획용 제안이며 실측 결과나 성과 약속이 아니다.                                |

## 2. 누구의 어떤 문제를 해결하는가

### 처음 시작하는 사람

만들고 싶은 것은 있지만 무엇부터 정해야 하는지 모른다. AI가 만든 화면이 그럴듯하면 완료로 생각하기 쉽고, 원하는 수정이 나오지 않으면 요청을 반복한다. 첫 화면을 만드는 것과 함께 수정의 기준을 익히도록 돕는다.

### 수업을 들은 사람

용어를 들어봤지만 혼자 작업할 때 어느 개념을 써야 하는지 연결하기 어렵다. 설명을 다시 전부 듣기보다 막힌 상황에 맞는 짧은 활동과 참고 자료로 돌아올 수 있어야 한다.

### 이미 작은 결과물을 만든 사람

기능을 추가하면서 범위가 커지고, 오류가 나면 무엇을 확인해야 할지 막힌다. 공통 화면 수정, 저장, 변경 관리, 검증 활동으로 필요한 부분만 보강할 수 있게 한다.

초기 권장 주대상은 첫 번째와 두 번째다. 숙련도는 가입 시 붙인 단일 레벨로 고정하지 않는다. 화면 구성에는 익숙하지만 데이터 저장에는 처음일 수 있기 때문이다.

## 3. 학습 성과와 품질 기준

목표는 문법 암기나 특정 도구의 버튼 숙지가 아니다. 활동 전후로 다음 행동이 달라지는지 확인한다.

| 능력 | 확인할 행동                                      | 남기는 결과                   |
| ---- | ------------------------------------------------ | ----------------------------- |
| 설명 | 목적·대상·원하는 동작을 구체적으로 말한다.       | 짧은 기획과 수정 요청         |
| 판단 | 여러 결과를 목적과 제약으로 비교한다.            | 선택과 그 이유                |
| 검증 | 완료 문구를 믿는 대신 실제 사용 흐름을 확인한다. | 확인한 조건과 관찰 결과       |
| 개선 | 문제가 재현되는 상황을 좁혀 다음 요청을 만든다.  | 수정 전후 기록과 다음 시도    |
| 전이 | 예제에서 경험한 원리를 자기 프로젝트에 사용한다. | 실제 적용 결과 또는 적용 계획 |

좋은 활동은 재미있는 조작, 분명한 발견, 내 작업에 쓸 결과를 연결한다. 재미만 있고 판단이 달라지지 않으면 휴식 콘텐츠로 분류하고, 학습 성과를 부풀리지 않는다.

주관적 선택에는 단일 정답을 주지 않는다. 디자인은 목적에 따른 장단점을 설명하고, 동작 검증은 관찰 가능한 조건으로 판정한다. AI가 문장이나 코드를 바꿨다는 사실만으로 개선되었다고 표시하지 않는다.

## 4. 기존 자료를 개선하고 전환하는 방식

기존 클래스 개요에는 설명·판단·수정이라는 목적과 상황 중심 설명 원칙이 이미 있다. 웹 기획 자료에는 목적·대상·기능·페이지·콘텐츠를 정리하는 활동이 있고, 회원 경험 문서에는 한 번에 할 일 하나와 결과물 피드백이라는 방향이 있다. 이를 워크북의 토대로 삼는다.

다만 이번 검토는 대표 문서와 일부 보강 자료 기준이다. 전체 HTML 교재·질문답변·시연의 정확성 검수가 끝난 것은 아니다. 실제 전환 전에는 단원마다 현재 원본과 변경 이력을 확인한다.

| 기존 재료                    | 워크북으로 바꿀 경험                          | 보강할 부분                                        |
| ---------------------------- | --------------------------------------------- | -------------------------------------------------- |
| 목적·대상·기능·페이지·콘텐츠 | 사용자 상황을 읽고 기능을 남기거나 미루기     | 선택마다 왜 필요한지, 언제 다른 선택이 맞는지 설명 |
| HTML·CSS·JS, 배치·반응형     | 구조·모양·동작을 하나씩 바꾸고 비교하기       | 용어 정의 뒤에 실제 수정 요청과 확인 조건 연결     |
| 상태·저장                    | 화면에서 바꾼 뒤 새로 열었을 때 결과 비교     | 화면 변화와 보존되는 데이터의 차이를 경험          |
| 컴포넌트                     | 공통 카드 수정이 여러 화면에 미치는 영향 비교 | 수정 범위와 다시 확인할 화면을 명시                |
| 프롬프트·AI 협업             | 빠진 조건을 보완하고 결과의 차이 관찰         | 만능 프롬프트 대신 관찰→추가 요청의 반복           |
| 배포·관리                    | 내 컴퓨터와 공유한 주소의 결과 비교           | 공개 후 확인과 수정까지 학습 범위에 포함           |
| Git·브라우저 검증 등 심화    | 변경 전후 비교, 문제 재현, 복구 범위 선택     | 도구 이름을 배우기 전에 필요한 상황 제시           |
| 질문답변·실제 막힘 사례      | 증상을 보고 다음 확인 행동을 고르기           | 개인 정보 제거, 해결 조건 검증, 관련 원리 연결     |
| 월요일 편지·개별 피드백      | 이번에 이어갈 일 하나와 짧은 피드백           | 특정 기수 일정과 운영 약속을 일반 과정에서 분리    |

전환할 때는 각 원고에 다음 질문을 적용한다.

1. 입문자가 실제로 언제 이 내용을 필요로 하는가?
2. 설명을 읽기 전에 관찰하거나 선택할 수 있는가?
3. 비유와 실제 화면의 용어가 연결되는가?
4. AI에게 요청할 말과 사람이 확인할 것이 함께 있는가?
5. 특정 기술을 무조건 써야 한다는 인상을 주지 않는가?
6. 직접 검증한 사실, 설명용 시뮬레이션, 제안이 구분되는가?

과거 일정·발표 분량·기수별 안내와 현재 제품 설명을 섞지 않는다. 특히 오래된 운영안의 미해결 표기를 현재 결정으로 가져오지 않는다.

## 5. 전체 학습 여정 제안

고정된 6주 수업 순서보다 제작 단계에 따라 묶는다. 처음에는 권장 순서로 안내하고, 경험이 있는 사람은 관련 활동으로 바로 들어갈 수 있게 한다.

| 단계                 | 사용자의 질문                   | 대표 활동                      | 내 프로젝트에 남는 것   |
| -------------------- | ------------------------------- | ------------------------------ | ----------------------- |
| 1. 무엇을 만들까     | 누구에게 어떤 도움을 주고 싶지? | 목적 구체화, 기능 덜어내기     | 목적 한 문장과 첫 범위  |
| 2. 첫 화면 만들기    | AI에게 무엇을 전달해야 하지?    | 콘텐츠 채우기, 요청 구성       | 첫 제작 요청과 화면     |
| 3. 화면 판단하기     | 예쁘지만 쓰기 편한가?           | 정보 순서, 여백, 모바일 비교   | 수정 기준과 개선 화면   |
| 4. 동작 만들기       | 누르면 어떤 변화가 있어야 하지? | 상태 전환, 입력과 오류 상황    | 동작 조건과 확인 기록   |
| 5. 기록 남기기       | 다시 들어와도 남아야 하나?      | 저장 범위 비교, 접근 상황 판단 | 데이터와 접근 요구사항  |
| 6. 공유하고 개선하기 | 다른 사람도 잘 사용할까?        | 공유 주소 확인, 변경 비교      | 공유 결과와 다음 개선점 |

단계 5의 로그인·데이터 관련 실제 실습은 별도 기술 검수 후 제작한다. 소개 페이지에 필요하지 않은 로그인이나 저장을 필수 과제로 넣지 않는다. 주제에 따라 필요한 단계만 확장한다.

## 6. 하나의 활동이 갖는 공통 흐름

| 순서 | 화면에서 하는 일                           | 설계 기준                                       |
| ---- | ------------------------------------------ | ----------------------------------------------- |
| 상황 | 익숙한 문제와 목표를 짧게 본다.            | 설명을 읽기 전에 무엇을 해결하는지 알 수 있다.  |
| 예상 | 무엇이 달라질지 선택하거나 생각한다.       | 오답을 벌점으로 만들지 않는다.                  |
| 실험 | 조작·비교·관찰로 결과를 확인한다.          | 조작과 결과의 인과가 보인다.                    |
| 해석 | 왜 그렇게 됐는지 짧게 읽는다.              | 용어는 방금 본 현상에 붙인다.                   |
| 적용 | 자신의 상황에 맞는 요청이나 기준을 만든다. | 예제 값 복사로 끝내지 않는다.                   |
| 확인 | 실제 결과를 살피거나 관찰 내용을 남긴다.   | 아직 실행하지 않은 것을 완료로 처리하지 않는다. |

모든 활동에 같은 조작을 강제하지 않는다. 배치는 직접 조절, 기획은 선택과 제외, 디자인은 비교, 디버깅은 재현과 원인 좁히기가 적합하다. 드래그가 있는 활동은 버튼·키보드 대안을 제공한다.

카피바라는 정답을 판정하는 선생보다 함께 관찰하는 동료로 둔다. “틀렸어요” 대신 “버튼은 보이는데, 이 방문자가 누를 이유도 보일까요?”처럼 다음 확인 행동을 제안한다. 매번 칭찬하거나 설명을 반복하지 않는다.

## 7. 첫 검증 과정 상세안

### 과정 이름과 범위

**내 소개 페이지를 만들고 한 번 제대로 고치기.**

계획용 예상 시간은 워크북 활동 30~45분, 외부 AI 제작 시간 별도다. 실제 시간은 파일럿에서 측정한다. 취업용 포트폴리오로 제한하지 않고 개인·브랜드·작은 모임 소개 중 하나를 고른다.

첫 과정은 로그인·결제·데이터베이스 없이 가능한 소개 페이지를 대상으로 한다. 외부 도구가 없는 사람은 예제 활동까지 경험할 수 있지만, 자기 프로젝트 적용은 별도 상태로 남긴다.

### 활동 1. 누구를 위한 첫 화면인가

상황: 카피바라의 작은 작업실 소개 페이지에 사진, 긴 인사말, 주소, 예약 안내가 한꺼번에 들어 있다. 인스타그램에서 처음 들어온 방문자가 작업실을 알아보고 방문 여부를 판단하도록 만들고 싶다.

- 행동: 첫 화면에 남길 정보 세 가지를 고르고 이유를 선택한다. 이후 방문 목적을 “행사 일정 확인”으로 바꾸어 다시 비교한다.
- 반응: 선택한 정보로 미리보기가 바뀐다. 일정 확인이 목표인데 일정이 숨겨졌다면 그 결과를 짚는다.
- 발견: 좋은 정보 순서는 방문 목적에 따라 달라진다.
- 내 적용: “누가, 무엇을 알아보고, 어떤 행동을 하게 할 것인가”를 한 문장으로 쓴다.
- 완료: 세 요소가 식별되는 문장을 남긴다. 문장 길이나 특정 표현으로 점수를 매기지 않는다.

### 활동 2. 이번에 만들 것만 남기기

상황: 소개·사진·위치·문의·회원가입·결제·후기·알림 등 기능 후보가 있다.

- 행동: 지금 필요 / 나중에 / 이번에는 제외로 나눈다. 초기 화면은 권장 세 가지를 먼저 고르게 하되 절대 제한으로 만들지 않는다.
- 반응: 선택한 기능에 따라 필요한 준비와 추가 고려사항을 보여준다. 임의의 비용·기간 숫자를 붙이지 않는다.
- 발견: 기능의 수보다 목적을 이루는 가장 작은 흐름이 중요하다.
- 내 적용: 첫 제작 범위와 제외 범위를 적는다.
- 완료: 최소한의 사용자 흐름이 설명되고, 나중으로 미룬 것이 구분된다.

### 활동 3. AI에게 첫 화면 부탁하기

상황: “예쁜 소개 사이트 만들어줘”만으로는 원하는 대상·콘텐츠·동작을 알 수 없다.

- 행동: 앞서 만든 목적, 대상, 기능, 실제 제목·소개글, 참고 방향을 요청에 넣는다. 부족한 내용은 직접 작성한다.
- 반응: 어떤 정보가 아직 비어 있는지 알려준다. 단순 글자 수로 프롬프트 품질을 채점하지 않는다.
- 실험: 조건이 다른 두 요청과 결과 예시를 비교한다. 예시는 사전 제작된 시뮬레이션임을 표시한다.
- 내 적용: 요청을 복사해 외부 AI 도구에서 제작하고 결과를 확인한다.
- 완료: 요청 작성은 ‘준비됨’, 실제 화면 확인은 ‘적용함’으로 분리한다. 복사 버튼 클릭만으로 제작 완료 처리하지 않는다.

### 활동 4. 예쁜 화면에서 쓸 수 있는 화면으로

상황: 첫 화면은 보기 좋지만 모바일에서 제목이 길고, 중요한 버튼이 눈에 띄지 않는다.

- 행동: 넓은 화면과 좁은 화면을 전환하며 문제를 찾고, 정보 순서·간격·배치를 한 번에 하나씩 바꾼다.
- 반응: 결과가 즉시 바뀐다. 개선 여부는 “제목이 잘리지 않는가”, “주요 행동이 구분되는가” 같은 기준으로 살핀다.
- 발견: 취향과 사용성 문제를 구분하고, 구체적인 변화로 요청할 수 있다.
- 내 적용: “모바일에서 제목이 버튼을 밀어내요. 제목 길이와 위쪽 여백을 줄이고, 넓은 화면도 함께 확인해줘”처럼 관찰과 요청을 연결한다.
- 완료: 수정 전 문제, 요청한 변화, 수정 후 관찰을 한 건 남긴다.

책상 정리 데모는 이 활동의 배치 보충 실험 후보로 둘 수 있다. 정식 채택 전에는 자기 화면의 수정 판단으로 이어지는지 확인한다.

### 활동 5. AI의 완료 보고를 직접 확인하기

상황: AI는 완료했다고 했지만 버튼이 엉뚱한 곳으로 이동하거나 작은 화면에서 내용을 가릴 수 있다.

- 행동: 중요한 버튼 사용, 좁은 화면 읽기, 다시 열기 등 자기 페이지에 필요한 확인을 직접 수행한다.
- 반응: 문제가 있으면 “어디에서 / 무엇을 했을 때 / 무엇을 기대했는데 / 실제로 무엇이 일어났는지”를 적게 한다.
- 내 적용: 재현 가능한 후속 요청을 만든다. 해결되지 않으면 막힌 상태와 다음 시도를 남긴다.
- 완료: 주요 흐름을 실제 확인했거나, 미해결 문제를 구체적으로 남겼다. 모든 문제가 해결돼야만 학습 기록을 남길 수 있는 구조는 피한다.

### 과정 종료 결과

목적 한 문장, 첫 기능 범위, 실제 제작 요청, 첫 화면, 수정 한 건, 확인 기록이 연결된다. 초안에서는 다운로드·복사 가능한 결과 묶음을 우선 검토한다. 계정 저장과 파일 업로드는 구현·개인정보 정책 결정 이후에 추가한다.

## 8. 화면 구성과 이동 흐름

### 워크북 홈

제안하는 중심은 ‘이어서 할 활동’과 ‘내가 만드는 것’이다. 기존 홈의 레이아웃 변경은 아직 승인되지 않았다. 주간 미션은 본 과정을 가리는 큰 과제가 아니라 선택 가능한 보조 경험으로 둔다.

### 과정 소개

무엇을 할 수 있게 되는지, 필요한 준비, 예상 활동 시간, 외부 도구 사용 여부, 남는 결과를 먼저 보여준다. 계정·유료 도구가 필요한 경우 시작 전에 안내하고 예제로 체험할 수 있는 범위를 구분한다.

### 활동 화면

데스크톱은 실험 화면과 조작·질문을 나란히 배치한다. 모바일은 상황→실험→조작→결과 순서를 유지하며, 실험 고정 영역이 조작 버튼을 가리지 않게 한다. 설명은 짧은 기본 문장과 펼쳐 읽는 원리로 나눈다.

항상 돌아가기, 초기화, 힌트, 지금 결과를 확인하는 방법이 있어야 한다. 색만으로 상태를 구분하지 않는다. 스크롤 영역에는 범위와 조작 안내를 표시한다.

### 내 작업으로 이동

외부 AI를 여는 단계에서는 요청 문장, 함께 전달할 자료, 돌아와서 확인할 항목을 한곳에 제시한다. 워크북이 외부 실행 결과를 자동으로 안다고 표현하지 않는다. 돌아왔을 때 결과가 없어도 예제로 계속 탐색할 수 있다.

## 9. 주간 미션 설계 제안

본 과정은 선행 경험을 따라 이어가고, 주간 미션은 할 수 있는 후보 안에서 변주·복습한다. 초기에는 추천 알고리즘보다 사용자가 자기 상황을 고르는 방식으로 충분하다.

### 후보를 고르는 순서

1. 현재 단계, 필요한 선행 경험, 사용할 기기, 외부 도구 필요 여부를 확인한다.
2. 미검증·수정 중·이용 불가능한 미션을 후보에서 제외한다.
3. 사용자가 고른 시간 여유와 관심 주제에 맞춘다.
4. 남은 후보 안에서 주간 미션 하나를 선택한다. 가능하면 바로 전 미션 반복을 피한다.
5. 후보가 없으면 조건을 무시해 배정하지 않고 기본 활동이나 직접 선택을 제안한다.

일주일 동안 같은 미션을 유지하고, 사용자가 바꾸거나 다음으로 미룰 수 있게 하는 안을 권장한다. 주가 바뀌어도 진행 중 기록은 유지한다. 실제 저장과 주차 경계 정책은 구현 전에 확정한다.

### 초기 후보 목록

| 미션                        | 필요한 상태           | 하는 일                           | 남길 결과        |
| --------------------------- | --------------------- | --------------------------------- | ---------------- |
| 목적을 한 사람에게 설명하기 | 아이디어 있음         | 소개 문장을 구체화                | 목적 한 문장     |
| 기능 하나 덜어내기          | 기능 후보 있음        | 지금 필요 없는 기능 분리          | 제외 이유        |
| 첫 화면의 주인공 고르기     | 예제 또는 초안 있음   | 핵심 정보 우선순위 변경           | 순서와 이유      |
| 버튼 문구 바꾸기            | 버튼 있음             | 행동이 드러나는 표현 비교         | 문구와 기대 행동 |
| 모바일로 이사하기           | 화면 있음             | 좁은 폭에서 문제 한 곳 찾기       | 수정 요청        |
| 여백 한 곳만 바꾸기         | 화면 있음             | 간격 변경 전후 비교               | 판단 기준        |
| 내용이 길어져도 괜찮을까    | 카드·목록 있음        | 긴 제목으로 확인                  | 깨지는 조건      |
| 아무것도 없을 때            | 목록·기록 화면 있음   | 빈 상태를 확인                    | 안내 문구        |
| 실패한 다음 행동            | 입력·요청 기능 있음   | 예제 실패 상황에서 다음 행동 설계 | 오류 안내        |
| 새로 열면 무엇이 남을까     | 상태 활동 경험        | 보존할 정보 구분                  | 저장 요구사항    |
| 수정 범위를 좁혀보기        | 여러 화면 있음        | 공통·개별 변화 구분               | 요청 범위        |
| 완료 보고 다시 확인하기     | AI 수정 결과 있음     | 실제 사용 흐름 실행               | 확인 기록        |
| 한 번에 하나씩 부탁하기     | 큰 요청 있음          | 작은 단계로 분리                  | 첫 요청          |
| 막힌 상황 설명하기          | 미해결 문제 있음      | 재현 조건 정리                    | 후속 질문        |
| 다른 사람이 눌러보기        | 공유 가능한 결과 있음 | 동의한 상대의 사용 관찰           | 발견 한 가지     |
| 내 선택의 이유 남기기       | 결과물 있음           | 채택·제외한 선택 정리             | 짧은 회고        |

시간과 난이도는 따로 다룬다. ‘도움 없이 해봄 / 힌트를 보고 해봄 / 아직 막힘’과 사용자의 체감 난이도를 참고하되, 완료 수만으로 능력을 단정하거나 다음 활동을 자동 잠금하지 않는다.

## 10. 콘텐츠 제작과 검수 운영

### 활동 명세에 남길 정보

활동 ID와 제목, 상황, 목표 행동, 선행 경험, 필요한 도구·기기, 입력과 조작, 결과 반응, 힌트, 완료 조건, 자기 프로젝트 적용, 접근성 대안, 원본 자료 위치, 검증일, 검증 환경, 콘텐츠 상태를 관리한다. 이는 작성 항목 제안이며 DB 스키마 확정이 아니다.

### 제작 절차

원본 확인 → 상황과 목표 행동 정의 → 활동 대본 → 간단한 동작 시제품 → 기술·학습 검수 → 입문자 관찰 → 시각 완성도 보강 → 공개 판단 순서로 진행한다.

처음부터 모든 활동에 고해상도 장면을 제작하지 않는다. 실제 행동이 학습으로 이어지는지 확인한 뒤, 배경·캐릭터·소품을 공통 미술 방향에 맞춰 만든다. 정답을 누르면 끝나는 형식이나 같은 조작만 반복되는 문제를 먼저 고친다.

### 공개 전 확인

- 실제로 조작할 수 있고 변화의 이유를 설명할 수 있는가?
- 시뮬레이션 결과를 실제 AI의 보장된 결과처럼 보이지 않는가?
- 모바일·키보드·확대 상태에서도 핵심 활동을 완료할 수 있는가?
- 잘못된 입력, 빈 상태, 실패 이후에도 다음 행동이 있는가?
- 적용 결과와 외부 도구 사용 여부를 정직하게 표시하는가?
- 외부 요금제·기능·절차는 공개 전에 직접 확인했는가?

### 빠르게 바뀌는 AI에 대응

오래가는 원리, 도구별 실행 안내, 새 기능 실험을 분리한다. 도구 화면이 바뀌면 해당 안내만 교체할 수 있어야 한다. 도구별 문서에는 확인 날짜와 검증 환경을 적고, 문제가 확인된 미션은 신규 추천에서 제외한다. 대체 경로와 기존 진행자의 안내를 마련한다.

자동 점검은 링크·레이아웃·정해진 시나리오에 사용하고, 실제 도구 동작과 설명의 정확성은 사람이 검수한다. 이 문서는 현재 도구 기능이나 가격을 새로 검증한 자료가 아니다.

## 11. 구현 범위와 제작 우선순위

| 순서         | 만들 것                                     | 다음 단계로 갈 조건                       |
| ------------ | ------------------------------------------- | ----------------------------------------- |
| 1. 원고 검토 | 첫 과정 5개 활동 대본과 기존 자료 대응표    | 목적·행동·완료 조건을 승우가 검토         |
| 2. 경험 검증 | 목적 정하기→요청 구성→결과 확인의 최소 연결 | 사용자가 안내 없이 흐름을 이해하는지 관찰 |
| 3. 시각 제작 | 검증된 활동의 배경·소품·UI                  | 조화와 조작 명확성을 함께 확보            |
| 4. 실제 적용 | 외부 AI 제작과 돌아와 확인하기              | 사용자가 실제 수정 한 건을 수행           |
| 5. 확장 판단 | 첫 과정 나머지 활동, 주간 후보와 기록       | 학습 효과와 제작·운영 부담을 검토         |

첫 검증에서 제외할 것: 플랫폼 내부 AI 실행, 자동 프로젝트 생성·배포, 계정·결제, 복잡한 추천, 레벨·인증서, 물리 엔진, 캐릭터 상시 애니메이션. 필요성이 확인되면 별도 설계한다.

공통 엔진을 먼저 만들지 않는다. 서로 다른 활동 두세 개를 만들어 본 뒤 반복되는 화면과 콘텐츠 구조만 추출한다. 예산과 일정은 대본·미술 범위·저장 방식이 정해진 뒤 산정한다.

## 12. 성공을 확인하는 방법

파일럿은 제안상 3~5명의 입문자와 수업 참여자 일부를 대상으로 한다. 작은 표본이므로 통계적 학습 효과를 주장하지 않는다. 행동 관찰과 인터뷰로 다음 제작 판단에 필요한 문제를 찾는다.

| 확인할 질문               | 수집할 근거                  | 개선 방향                     |
| ------------------------- | ---------------------------- | ----------------------------- |
| 시작할 일을 알았나?       | 첫 행동과 도움 요청 지점     | 상황 설명·조작 안내 수정      |
| 변화의 이유를 이해했나?   | 조건을 바꾼 새 예제에서 설명 | 암기 유도와 비유의 한계 수정  |
| 자기 작업에 옮겼나?       | 실제 수정 요청과 결과        | 전이 단계의 안내 보강         |
| 결과를 검증했나?          | 실제 실행한 확인과 발견      | 체크 표시 중심 완료 방식 수정 |
| 막혀도 이어갔나?          | 힌트 이후 다음 행동          | 힌트 단계와 실패 피드백 개선  |
| 즐거움이 학습에 기여했나? | 조작 후 설명과 사용자 반응   | 불필요한 장식·반복 제거       |

완료율만 높고 이유를 설명하지 못한다면 성공으로 보지 않는다. 가벼운 체험 완료와 자기 프로젝트 적용 완료는 구분한다. 상세 행동 기록이나 결과물 수집은 동의와 보관 범위를 정한 뒤 진행한다.

## 13. 주요 위험과 대응

| 위험                         | 대응                                                   |
| ---------------------------- | ------------------------------------------------------ |
| 예쁜 미니게임 모음에 머묾    | 모든 핵심 활동에 자기 프로젝트로 옮기는 결과를 둔다.   |
| 처음부터 제작 범위가 커짐    | 첫 과정의 최소 흐름부터 검증하고 미술을 보강한다.      |
| 외부 AI 결과가 예시와 다름   | 정답 화면 복제보다 목적·동작·확인 기준으로 비교한다.   |
| 도구 비용·설치가 진입을 막음 | 예제 체험과 실제 제작 단계를 분리해 사전 안내한다.     |
| 초보에게 설명이 부족함       | 짧은 기본 안내와 선택형 원리 설명, 단계별 힌트를 둔다. |
| 익숙한 사람에게 반복이 됨    | 예제로 확인 후 필요한 활동만 선택할 수 있게 한다.      |
| 개인화가 잘못된 미션을 줌    | 단계 직접 선택과 교체·보류를 허용한다.                 |
| 운영 부담이 증가함           | 도구별 안내 분리, 검증 상태 관리, 피드백 범위 명시.    |

## 14. 검토 후 결정할 사항

1. **대상:** 독학 입문자까지 포함할지, 클래스 참여자를 먼저 대상으로 할지.
2. **첫 과정:** 소개 페이지 제작·개선을 첫 검증 대상으로 삼을지.
3. **제작 환경:** 초기에는 외부 AI 도구를 사용하는 방식에 동의하는지.
4. **연결성:** 하나의 프로젝트에 결과가 쌓이는 과정과 자유 체험의 비중.
5. **주간 미션:** 첫 과정 검증 이후 도입할지, 초기에는 목록만 제공할지.
6. **기록:** 파일 복사·다운로드부터 시작할지, 별도 저장 설계가 필요한지.
7. **책상 데모:** 배치 보충 활동으로 채택할지, 미술·조작 참고로만 둘지.

권장 다음 작업은 첫 과정 5개 활동의 대본 검토다. 먼저 대상과 첫 과정을 정한 뒤, ‘목적 정하기’ 한 편을 실제 화면 문구·선택지·결과 피드백까지 작성해 경험을 검증한다.
