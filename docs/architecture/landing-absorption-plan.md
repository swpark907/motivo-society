# motivo.kr Supabase 프로젝트 위로 플랫폼 올리기 — 흡수 계획 (2026-11-13)

## 결정 (2026-11-13 승우)

- 플랫폼은 **대표가 운영 중인 motivo.kr(`../motivo-class-landingpage`)의 Supabase 프로젝트**를 같이 쓴다. 새 프로젝트를 만들지 않는다.
- 그 회원들은 이 플랫폼으로 흡수된다. **기존 데이터가 깨지지 않는 선에서** 먼저 흡수한다.
- 지금까지 플랫폼은 로컬 Supabase(Docker)에서 시험장 데이터로만 돌았다. 운영 DB에 적용한 것은 아직 없다.

## 비교 결과 (레포의 SQL 파일 기준, 2026-11-13)

대표 레포의 `supabase/*.sql`과 이 레포의 `supabase/migrations/*.sql`을 비교했다. **운영 DB에 대시보드로 직접 바꾼 것이 있으면 여기에 안 잡힌다** — 적용 전에 실제 DB 스키마를 내려받아 다시 비교한다.

| 구분        | 겹침                              | 메모                                                                                      |
| ----------- | --------------------------------- | ----------------------------------------------------------------------------------------- |
| 테이블      | **`public.profiles` 하나**        | 나머지(신청·수강·소개·피드백·설문·퀴즈·스페이스 출석·도움·라운지·퀴즈)는 이름이 안 겹친다 |
| 함수        | 없음                              |                                                                                           |
| 로그인 계정 | 같은 `auth.users`를 쓴다(좋은 점) | motivo.kr은 **이메일+비밀번호**, 플랫폼은 **이메일 매직링크**                             |

### `profiles` 충돌 — 같은 이름, 다른 물건

|           | motivo.kr의 `profiles`                                                         | 플랫폼의 `profiles`                                    |
| --------- | ------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 담는 것   | **개인정보**: 실명, 나이, 이메일, 전화, 유입 경로, 관심사, 경험치, 스태프 여부 | **공개 프로필**: 닉네임(고유), 소개, 상태, 온보딩 시각 |
| 필수 값   | 실명·나이·이메일·전화·유입 경로·관심사 모두 필수                               | 닉네임만 필수                                          |
| 읽기 권한 | 본인 + (아래 참고)                                                             | **누구나 읽기**(`using (true)`)                        |
| 만드는 곳 | motivo.kr 가입 API                                                             | 플랫폼 온보딩                                          |

**하나로 합치면 안 된다.** 플랫폼 정책(누구나 읽기)이 그대로 붙으면 모든 회원의 이메일·전화가 공개된다. 반대로 motivo.kr의 필수 값(나이·전화) 때문에 플랫폼 온보딩(닉네임만 받음)이 실패한다. 또 플랫폼 마이그레이션은 `create table public.profiles`라서 이미 있는 테이블 앞에서 멈춘다.

## 흡수 방식 (제안)

1. **motivo.kr의 `profiles`는 그대로 둔다.** 이름·컬럼·정책·코드 모두 손대지 않는다. 운영 중인 서비스가 깨지지 않는 가장 확실한 길이다.
2. **플랫폼의 공개 프로필 테이블 이름을 바꾼다**(예: `public.accounts`). 운영 DB에 올리기 전, 이 레포의 마이그레이션·타입·코드에서 한 번에 바꾼다. 두 테이블은 같은 `id`(= `auth.users.id`)로 1:1 연결된다. 데이터를 옮길 필요가 없다.
3. **기존 회원이 플랫폼에 처음 들어오면** 온보딩에서 닉네임만 정하면 된다. 실명은 공개 닉네임으로 쓰지 않는다(개인정보). 관심사는 motivo.kr 값이 있으면 미리 채워 준다(값 체계가 달라 대응표가 필요하다).
4. **로그인:** 기존 회원은 비밀번호에 익숙하다. 플랫폼 `/login`에 "비밀번호로 로그인"을 함께 두는 안을 권한다(같은 계정이라 그대로 된다). 매직링크만 두어도 같은 이메일로 들어올 수는 있다.
5. **역할은 따로 둔다.** motivo.kr의 `member_role = 'staff'`(클래스 운영진)와 플랫폼의 `platform_staff`(소유자)·`hosts`(호스트 자격)는 뜻이 달라 합치지 않는다.
6. **플랫폼에서 새로 가입한 사람**에게는 motivo.kr `profiles` 행이 없다. motivo.kr의 회원 화면이 이 경우를 어떻게 다루는지(가입 화면으로 보내는지) 확인한다.

## 적용 순서 (운영 DB를 깨지 않기 위해)

1. **이 레포에서 준비:** 공개 프로필 테이블 이름 바꾸기, 비밀번호 로그인(선택), 관심사 대응표. `pnpm check` · `pnpm test:db` · e2e 통과.
2. **운영 스키마 내려받기:** 대표 프로젝트의 실제 스키마를 받아(`supabase db pull` 등) 이 레포의 기준 마이그레이션으로 삼는다. 대시보드에서 바꾼 것까지 잡힌다. 이후 변경은 한 가지 방식(마이그레이션)으로만 한다.
3. **복제본에서 먼저:** 운영 데이터를 복제한 곳(Supabase 브랜치 또는 복제 프로젝트, 로컬)에 플랫폼 마이그레이션을 올리고, 플랫폼 e2e와 **motivo.kr 주요 화면(가입·로그인·클래스룸·스페이스)** 을 함께 확인한다.
4. **백업 확인 후 운영 적용:** 백업 시점을 확인하고, 사람이 적은 시간에 적용한다. 적용 직후 motivo.kr 주요 화면을 다시 확인한다.
5. **되돌리기 준비:** 플랫폼 마이그레이션은 기존 테이블을 바꾸지 않고 새 테이블만 더하므로, 문제가 생기면 플랫폼 쪽 테이블만 걷어낼 수 있다.

## 대표에게 필요한 것

- Supabase 조직에 승우(또는 작업 계정) 초대, 프로젝트 요금제(Free/Pro) 확인.
- 대시보드에서 SQL 파일 밖으로 바꾼 것이 있는지.
- 운영 적용 시간대 승인.

## 함께 확인할 것 — motivo.kr 개인정보 읽기 범위

레포의 SQL 기준으로 `profiles`의 읽기 정책 `profiles_select_self_or_enrolled`는 "본인이거나, **읽는 사람이 클래스 수강생이면**" 읽기를 허용하고, 로그인한 사람에게 테이블 전체 읽기 권한이 있다. 이대로라면 **수강생 한 명이 다른 회원 모두의 이메일·전화번호를 읽을 수 있다.** 스페이스용 공개 보기(`space_public_profiles`)를 따로 만든 것을 보면 의도는 이름·경험치만 공개하는 것으로 보인다. 운영 DB의 실제 정책을 확인하고, 다르지 않다면 흡수와 별개로 먼저 고치는 것을 권한다(대표 확인 필요).
