# 관리자·콘텐츠 운영 아키텍처 검토

2026-10-16. 현재 저장소 코드와 에디토리얼 문서 v1을 기준으로 한 제안이다. 개발용 편집 실험실은 구현했으며, 운영 관리자·권한·DB·발행 서버는 구현하지 않았다.

## 결론

같은 Next.js 앱 안에 운영용 `/admin`을 두고, **관리자 화면 → 서버 명령 서비스 → 저장소 어댑터**로 나눈다. 아티클 편집기와 공개 화면은 **같은 문서 스키마와 렌더러**를 쓴다. 읽기 콘텐츠에는 작성 중인 개정본과 공개 중인 개정본을 별도로 둔다. 관리자 메뉴별 페이지에 DB 작업·검증·권한 판단을 복제하지 않는다.

지금은 `/demo/admin`에서 개발용 흐름을 검토한다. 인증 없는 `/admin`을 실제 운영 경로처럼 열지 않는다. 이번 실험실은 development 환경에서만 열리며 브라우저 IndexedDB에 편집 내용과 업로드 사진을 자동 임시 저장한다. 서버 파일·DB·발행 상태는 바꾸지 않는다. 필요한 내용은 JSON으로 내보낼 수 있다.

## 1. 현재 코드에서 확인한 사실

| 영역             | 현재 코드와 상태                                                                                       | 설계에 주는 영향                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 공통 화면        | `src/app/layout.tsx`가 GNB를 모든 페이지에 직접 붙인다                                                 | 운영 관리자 적용 시 공개/관리 레이아웃 분리가 필요하다     |
| 공개 내비게이션  | `src/lib/nav.ts`의 Yard·Library·Article·Workbook                                                       | 관리자 메뉴를 이 목록에 섞지 않는다                        |
| 정식 아티클      | `src/lib/content/articles.ts`, `content/articles/*.mdx`                                                | 기존 검증·영구 URL을 보존한 이관 경로가 필요하다           |
| Library          | `src/lib/content/library.ts`와 별도 frontmatter                                                        | 카테고리·기술 자료 정보는 아티클과 별도로 유지한다         |
| Yard             | `src/lib/content/yard.ts`의 kind/status/일정                                                           | 클래스·모임의 운영 상태를 글의 발행 상태와 혼동하지 않는다 |
| 워크북 테스트 글 | `src/lib/content/workbook-readings.ts`가 JSON5편을 읽는다                                              | 편집기 첫 실험 대상으로 적합하다                           |
| 문서 스키마      | `workbook-editorial-schema.ts`, 기계용 JSON Schema                                                     | 서버·편집기·AI가 동일 명세를 사용한다                      |
| 현재 데이터      | Article1편·Yard1편, Library MDX 파일 없음, 워크북 테스트5편                                            | 거대한 CMS 이관보다 작은 기능부터 검증하기 좋다            |
| 인증·저장        | 이 저장소에는 로그인 SDK·관리자 권한·DB 쓰기 코드·관리 API 없음                                        | 운영 인증과 저장소는 별도 결정과 연결 작업이 필요하다      |
| 정식 OG          | Article은 title/description, Library는 OG title/description을 설정하고 OG image는 개별 설정하지 않는다 | 정식 이관의 발행 계약에 OG image 검증도 넣어야 한다        |

형제 운영 서비스의 회원·Q&A·신청 데이터를 이번 설계로 옮기지 않았다. 관리자부터 만든다는 이유로 미확정 회원·결제 정책을 앞당기지 않는다.

## 2. 콘텐츠와 문서 스키마의 완료 범위

에디토리얼 v1은 표지4종, 본문9블록(핵심 메모·질문과 답변 추가), 허용된 배치·폭·정렬·크롭, 관련 글 연결, 안정적인 블록 ID를 정의했다. 다섯 JSON 샘플이 이 명세를 사용하며 JSON Schema와 런타임 명세의 일치를 검사한다.

이것은 **글의 표현 문서**다. 다음 운영 정보까지 문서 본문에 섞지 않는다.

- 로그인 세션·관리자 권한·비밀키
- 작성자와 검토자의 신원
- 서버 저장 시각·공개 상태·현재 공개 개정본
- 댓글·회원·결제·학습 진행 기록

현재 원문에는 slug/title 같은 검색용 메타데이터도 포함된다. 운영 저장소가 색인용 필드를 별도로 보관하면 명령 서비스에서 동일한 정규화 결과로 함께 갱신하고 일치 여부를 확인한다. 두 곳을 각각 수정하는 API는 두지 않는다.

범용 미디어 관리로 옮길 때는 현재 `/images/workbook/notes/` 로컬 자산 제약을 asset ID/허용 URL 계약으로 이관해야 한다. 이 변경을 단순히 모든 외부 URL 허용으로 처리하지 않는다. v1의 현재 범위를 일반 업로드 기능까지 완료한 것으로 표현하지 않는다.

## 3. 권장 코드 경계

운영 전환 시의 제안 구조다. 아래 전체 폴더를 미리 구현한 것은 아니다.

```text
src/app/
  layout.tsx                  폰트·전역 스타일만 공통
  (public)/
    layout.tsx                공개 GNB
    article/... library/... yard/... workbook/...
  (admin)/admin/
    layout.tsx                세션 확인·관리자 셸
    page.tsx                  실제 검토 대기·최근 편집 목록
    content/page.tsx          콘텐츠 목록·필터
    content/[id]/page.tsx      유형별 편집 진입
    review/...                검토·발행
    media/...                 사진·캡션·사용처
    home/...                  홈 편집 슬롯
src/components/
  ArticleEditor/              편집 세션·컨트롤·미리보기 프레임
  EditorialArticle/           공통 표지·본문·블록 렌더러
  AdminShell/                 운영 전환 때 추가할 메뉴·레이아웃
src/lib/
  editorial/                  편집 조작·검증. React·DB 의존 없음
  content/                    공개 콘텐츠의 읽기 경계·문서 스키마
  admin/
    access.ts                 서버에서 권한 확인
    content-service.ts        저장·검토·발행 명령
    repositories/             DB/파일 등 저장 구현을 감춤
```

라우트 그룹 `(public)`·`(admin)`은 URL을 바꾸지 않는다. 루트 layout 하나를 유지하고 그룹별 중첩 layout에서 GNB와 AdminShell을 분리하는 안이다. 지금은 다른 워크북 작업과 공유하는 전체 라우트를 이동하지 않았다.

클라이언트 편집기에는 문서·허용된 이미지 정보 등 필요한 DTO만 전달한다. 저장소 구현과 관리자 비밀정보를 import하지 않는다. 서버는 클라이언트에서 이미 검증했더라도 다시 스키마·참조·권한을 검증한다.

## 5. 저장 모델과 발행 경계

다음은 저장 기술과 독립적인 논리 모델 제안이다. 실행할 DB 마이그레이션은 아니다.

| 모델             | 주요 정보                                                                     | 목적                             |
| ---------------- | ----------------------------------------------------------------------------- | -------------------------------- |
| ContentEntry     | 내부 id, kind, 영구 slug, 작성 중 revision ID, 공개 revision ID               | 글의 정체성과 공개 포인터        |
| ContentRevision  | revision ID, entry ID, 형식 버전, 문서 JSON, 작성자, 생성 시각, 부모 revision | 개정본 보존·되돌리기             |
| ContentReview    | revision ID, 검토자, 실제 verifiedAt, 근거·검토 결과                          | 검토한 내용과 발행할 내용을 묶음 |
| PublicationEvent | entry/revision ID, 발행·철회 동작, 실행자·서버 시각                           | 변경 이력                        |
| Asset            | 내부 id, 저장 위치, alt/caption, 출처·권리 정보                               | 업로드·이미지 이관 후 관리       |

초안 저장은 새 revision을 만들고 초안 포인터만 바꾼다. 공개 화면은 published revision만 읽는다. 검토는 revision에 귀속되므로 본문이 달라지면 새 개정본의 검토가 필요하다. 공개 포인터 변경과 이력 기록은 하나의 원자적 작업으로 처리한다.

예상 명령 계약은 다음 정도로 시작할 수 있다.

```text
saveDraft(entryId, expectedDraftRevisionId, document)
requestReview(revisionId)
recordReview(revisionId, verificationEvidence)
publish(entryId, revisionId, expectedPublishedRevisionId)
withdraw(entryId, expectedPublishedRevisionId)
```

같은 글을 두 탭에서 수정했을 때 expected revision이 다르면 충돌을 알려주고 자동 덮어쓰지 않는다. 게시물 삭제보다 공개 철회·보관을 기본으로 검토한다. 공개 URL 변경이 필요하면 리다이렉트 기록을 함께 설계한다.

## 6. 권한과 발행 검증

첫 운영은 허용된 관리자 목록으로 단순하게 시작하되, 서버 코드는 `content:write`, `content:review`, `content:publish`, `media:write`, `home:edit`처럼 동작별로 검사하는 것을 권장한다. 실제 권한 배정·자기 글 검토 허용 여부는 사용자 결정이 필요하다. 공개 회원 가입이나 유료 회원 상태가 관리자 권한을 주지 않는다.

- layout의 접근 확인은 화면 진입 안내다. 각 서버 데이터 읽기·쓰기와 발행 명령에서도 권한을 확인한다.
- 입력된 authorId·role·검증 완료 표시를 신뢰하지 않는다. 실행자는 서버 세션에서 결정한다.
- 형식 검증과 콘텐츠의 사실 검증은 다르다. JSON 검증 통과가 실사용 검증 완료를 뜻하지 않는다.
- verifiedAt은 실제 확인한 날짜이며 저장 버튼을 누른 오늘 날짜로 자동 채우지 않는다. reviewedAt 같은 서버 기록 시각과 구분한다.
- 외부 작성 도구가 나중에 연결되면 같은 명령 서비스와 권한·검증 경계를 재사용한다.

확인 근거는 현재 설치된 Next 문서의 authentication/data-security/route-groups 가이드다. 인증 제공자·DB·이미지 저장소 선택은 이번에 임의로 확정하지 않았다.

## 7. 실제 구현한 편집 실험실

- `/demo/admin`: 관리자 구조 설명과 편집기 진입.
- `/demo/admin/articles`: 다섯 샘플 선택, 미리보기 구간 클릭 → 해당 구간의 정렬·스타일 버튼, 선택한 문구의 개별 수정, 접힌 JSON 원문 적용/취소/내보내기. 좌측 속성 폼과 블록 목록은 기본 화면에서 제거했다.
- `/demo/editorial-preview`: 별도 viewport의 개발용 미리보기. 부모 편집기와 같은 출처·해당 frame 메시지만 받고 다시 문서를 검증한다.
- 공개 워크북과 프리뷰가 `EditorialArticle`·`EditorialBlocks`를 공유한다.
- 원문 편집은 적용 버튼이 있고, 미적용 원문이 있으면 시각 모드 전환·내보내기를 막는다. 잘못된 입력은 마지막 유효 미리보기를 유지한다.
- 글별 편집은 브라우저 임시 저장으로 복원하며 JSON 내보내기로 결과를 가져갈 수 있다.
- 레이아웃·각 페이지에 development 조건을 두어 production에서는 notFound 처리한다. noindex는 별도로 제공하며 권한 장치로 취급하지 않는다.

고정 좌표의 자유 캔버스·파일 업로드·AI API 호출·Markdown 자동 변환·로그인·DB 쓰기·발행은 연결하지 않았다. v1의 소수 배치 선택이 실제 편집에 충분한지부터 시험한다.

## 8. 운영 전환 순서와 결정할 것

1. 이 실험실에서 다섯 글의 편집·미리보기 경험을 확인하고 문서 v1 수정 필요를 판단한다.
2. 정식 `/admin` 레이아웃, 인증 제공자·허용 관리자·동작 권한을 결정한다. 기존 운영 서비스와의 회원 통합 여부는 별도 결정으로 유지한다.
3. 저장소 어댑터·개정본·충돌 처리·검토/발행 명령을 연결한다. 사용자 요청 없이 DB를 생성하거나 기존 서비스를 변경하지 않는다.
4. 프리뷰 글과 정식 Article/Library의 이관 정책, 영구 URL·OG·사람 검증 관문을 확인한 뒤 일부 콘텐츠부터 이관한다.
5. 실제 운영 필요에 따라 미디어·홈 슬롯·Yard 소개 관리로 넓힌다.

현재 가장 먼저 정할 것은 관리자 사용자의 범위와 인증/저장소 연결 방식이다. 그 전에도 문서 편집기 자체는 독립적으로 검토할 수 있다.

## 9. 이번 검증 결과

- `pnpm check`: typecheck·lint·format·순수 로직31개 통과.
- 관리자 편집기와 기존 아티클 E2E: PC·모바일8개 통과. 최종 이미지 허용 목록·편집 복귀 보정 후 관리자4개도 재확인했다.
- 구간 선택·정렬 변경·문구 변경, 샘플별 편집 유지, 잘못된 JSON의 반영 차단, JSON 다운로드, 새로고침 복원, 공개 원본 미변경을 확인했다.
- PC1440px·모바일390px에서 화면과 미리보기 전환을 확인했다. 미리보기 자체의 viewport는 PC1200px·모바일390px로 분리했다.
- 자체 코드 검토에서 원문 취소 시 기존 오류 상태가 잘못 지워지는 경우와 입력란 라벨 연결을 보정했다. 클라이언트 경계에 파일 로더·비밀정보가 들어가지 않는 것도 확인했다.
- 운영 인증·DB·실제 발행·production 빌드 검증은 이번 범위에 포함하지 않았다.

### 미리보기 직접 조작 보정 (2026-10-16)

좌측 폼을 제거하고 구간 선택 도구로 전환했다. 표지·문단·목록·인용·사진·복합 구간마다 허용된 배치만 제공하고, 추가 설정과 문구 수정은 필요할 때 연다. 선택 도구는 공개 렌더러 바깥의 개발 미리보기에서만 제공한다. 모든 선택 옵션의 스키마 유효성·원본 불변성을 순수 테스트로 확인했으며, pnpm check(33개)와 관리자 PC·모바일 E2E(4개), 기존 읽기 E2E(4개)가 통과했다. PC·모바일 실제 화면도 검수했다.

### 구간 종류·표현 확장 검증 (2026-10-16)

구간 종류 전환과 되돌리기, 문자 중심24개 표현을 추가했다. 종류 전환의 원문 보존·사진 소실 방지·스키마 유효성을 확인했고, 원문에서 선택 구간을 제거한 뒤에도 미리보기가 유지되도록 선택 유효성을 보정했다. 관리자·읽기 PC/모바일 E2E10개 통과. 세부 명세는 [구간 카탈로그](../product/editorial-block-catalog.md)를 따른다.
