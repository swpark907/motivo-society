# 플랫폼 백엔드 큰 그림 (초안)

2026-11-01. 세부 스키마가 아니라 **도메인 경계와 흐름**을 먼저 맞추는 문서다. 근거 조사는 [platform-benchmark-research.md](platform-benchmark-research.md). 아래 "확정"은 사용자가 결정한 것, "제안"은 아직 논의 중인 것이다.

## 확정된 것

- **결제 방향 (2026-11-01).**
  - 장기: 플랫폼이 직접 결제를 받는다.
  - 단기: 계좌이체 등으로 받고, 운영진이 입금을 확인한 뒤 상태를 바꾼다.
  - 형제 서비스(motivo-class-landingpage)의 `applications`(pending → paid, 24시간 만료) 흐름과 같은 방식이다.
- **진행 방식.** 세부 설계보다 큰 그림을 먼저 맞춘다.
- **B2C 먼저 (2026-11-01).** 기업·단체 확장은 나중에 한다. 그때는 "조직" 개체에 개인 계정이 소속되는 구조로 풀고, 지금은 자리만 남긴다.
- **계정은 하나다 (2026-11-01).** 호스트와 참석자를 계정 종류로 나누지 않는다. 같은 계정에 호스트 자격, 클럽 레이어, 모임별 역할이 덧붙는다.

- **Supabase 환경 (2026-11-01).**
  - 개발: 운영 프로젝트(motivo-class-landingpage)를 그대로 쓰지 않고, 별도 개발 프로젝트를 만든다. 스키마만 복제하고 실제 회원 데이터는 복사하지 않는다. 가짜 데이터로 개발한다.
  - 기준점: 운영 DB의 실제 스키마를 읽기 전용으로 덤프해 이 레포의 첫 마이그레이션으로 삼는다.
  - 최종 운영: 기존 운영 프로젝트를 키워서 쓴다(A). 개발 프로젝트에서 검증한 마이그레이션만 적용한다.
  - 전환 여지: 덤프를 검토하거나 설계를 진행하면서 크게 바뀌어야 한다고 판단되면, 새 운영 프로젝트를 만들고 흡수 때 옮기는 방식(B)으로 전환할 수 있게 열어 둔다.

## 개념과 용어 (가칭, 2026-11-01)

| 개념                        | 가칭 | 코드        | 정의                                                                      |
| --------------------------- | ---- | ----------- | ------------------------------------------------------------------------- |
| 사람들이 집단을 이루는 단위 | 클럽 | `Club`      | 멤버 명단과 운영진이 있는 소속 단위. 한 사람이 여러 클럽에 들어갈 수 있다 |
| 그 안에서 이뤄지는 게더링   | 모임 | `Gathering` | 날짜·장소·정원이 있는 한 번의 만남. 신청 → 확정 → 참석                    |
| 다회차로 진행되는 모임      | 시즌 | `Series`    | 회차 묶음. 보통 한 번 등록하고, 각 회차는 모임이다                        |

- 클럽 1 → N 모임(단발), 클럽 1 → N 시즌 1 → N 모임(회차).
- "매주 수요일" 같은 반복 일정은 모임을 쉽게 만드는 기능이고, 시즌(묶음 등록·정원·가격·환불 단위)과 다르다.
- 모임마다 "클럽 멤버 전용 / 누구나"를 설정한다.
- 온라인 워크북 클래스는 시즌이 아니라 강의 쪽 개념이다. 이용권으로 시즌·모임과 연결한다.
- **모임은 클럽 밖에서도 열린다 (2026-11-01 확정).** 클럽 밖에서 호스트 개인이 여는 단발 모임과, 클럽 안에서 권한 있는 사람이 여는 모임이 둘 다 있다.
  - 제안: 같은 `Gathering` 개체에 **주최**(개인 또는 클럽)를 두고, 누가 열 수 있나·누가 관리하나·공개 범위를 주최 종류별 규칙으로 나눈다. 출석·신청·결제 흐름은 하나로 쓴다.
  - 개인 주최: 호스트 자격이 있어야 연다. 관리는 주최자와 그가 지정한 진행자가 한다.
  - 클럽 주최: 클럽 레이어의 "모임 만들기" 권한으로 연다. 관리는 클럽 레이어를 따르고, "멤버 전용 / 누구나"를 고를 수 있다.
  - 미결: 시즌도 클럽 밖에서 열 수 있게 할지.

## 사람과 역할의 세 층 (제안)

| 층     | 정하는 것                              | 역할                                              |
| ------ | -------------------------------------- | ------------------------------------------------- |
| 플랫폼 | 이 사람이 플랫폼에서 무엇을 할 수 있나 | 플랫폼 운영진 역할, 호스트 자격                   |
| 클럽   | 이 클럽 안에서 무엇을 할 수 있나       | 관리자 · 운영진 · (관리자가 추가한 레이어) · 멤버 |
| 모임   | 이 한 번의 모임에서 무엇을 하나        | 진행자 · 참석자                                   |

**클럽 레이어.**

- 순서가 있는 레이어다. 관리자(최상위, 삭제 불가, 최소 1명)와 멤버(최하위)는 고정이다. 관리자는 그 사이에 레이어를 추가하고 이름과 권한을 정한다.
- 권한은 플랫폼이 정한 목록에서만 고른다.
- 안전 규칙:
  - 자기보다 아래 레이어만 관리한다.
  - 자기가 가진 권한만 남에게 준다.
  - 마지막 관리자는 양도 없이 나갈 수 없다.
  - 레이어를 지우면 그 사람들은 멤버로 내려간다.
  - 연락처·입금·환불 같은 민감 권한은 기본적으로 관리자만 갖는다.
  - 레이어 수에 상한을 둔다.
- 레이어는 권한 전용으로 두고, 칭호나 뱃지는 나중에 별도 기능으로 붙이는 것을 제안한다(미결).

**호스트 자격.** 계정에 붙는 상태다. 미신청 → 무료 모임 개설 → 유료 모임 개설(실명·정산 정보 필요) → 정지. 누구에게 어떤 조건으로 열지는 정책으로 정하며, 구조는 바꾸지 않고 문만 넓힐 수 있다.

**플랫폼 운영진.**

- 클럽 레이어와 무관하고, 초대로만 부여하며 2단계 인증을 요구한다.
- 기존 [관리자 운영 정책](admin-operating-policy.md)의 콘텐츠 역할(소유자·발행 관리자·편집자)을 모임·거래·회원 운영까지 넓힌다.
- **처음에는 소유자 역할 하나로 시작한다 (2026-11-01 확정).** 사람이 늘면 나눈다.
- 나눌 때를 대비해, 서버는 처음부터 역할 이름이 아니라 동작별 권한으로 검사한다: 콘텐츠, 커뮤니티 운영(호스트 자격 심사, 신고 처리, 클럽 정지), 거래(입금 확인, 환불), 회원 정보 열람. 소유자는 이 권한을 모두 가진다.
- 운영진이 클럽에 개입한 조치와 개인정보 열람은 모두 이력으로 남긴다. 가격·환불 정책 변경은 대표 승인 규칙을 따른다.

## 도메인 지도 (제안)

```text
            모임                강의               콘텐츠
     (그룹·시즌·회차·참가)   (클래스·수업·진도)   (아티클·라이브러리)
              ▲                  ▲
              └──── 이용권 ───────┘                소통·신뢰
     거래 ───▶ (참여·수강 자격)                     (공지·신고·후기)

  ─────────────── 계정 · 권한 (운영진 · 호스트 · 멤버, 대상별 역할) ───────────────
```

| 도메인     | 하는 일                                        | 한 줄 원칙                                                                         |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| 계정·권한  | 로그인한 사람이 누구이고 무엇을 할 수 있나     | 회원 여부와 관리 권한은 별개다. 호스트 권한은 "이 모임의 호스트"처럼 대상에 붙는다 |
| 모임       | 그룹 → 시즌·반복 → 회차, 참가 신청과 실제 참석 | 소모임식 자유 모임과 동행클럽식 시즌제를 같은 구조로 표현한다                      |
| 강의       | 클래스 → 단원 → 수업, 학습 진도와 기록         | 지금 브라우저에 있는 워크북 진도를 이 경계로 옮긴다                                |
| 거래       | 주문, 결제 확인, 환불, (나중에) 정산           | 결제 수단이 바뀌어도 주문과 상태 흐름은 같다                                       |
| **이용권** | 누가 무엇에 참여하거나 수강할 자격이 있나      | 거래, 운영진 부여, 수료 등 출처가 달라도 여기 한 곳에서 판정한다                   |
| 콘텐츠     | 아티클·라이브러리 발행                         | 기존 관리자 설계(개정본·검토·발행)를 따른다                                        |
| 소통·신뢰  | 공지, 알림, 신고·제재, 후기                    | 모임이 생기면 함께 필요해진다                                                      |

**핵심은 이용권이 가운데 있다는 점이다.** 모임과 강의는 "돈을 냈나"를 직접 보지 않고 "이용권이 있나"만 본다. 그래서 다음이 모두 같은 장치로 풀린다.

- 계좌이체 수동 확인이든 나중의 PG 결제든 결과는 이용권 발급이다.
- 무료 초대와 운영진 부여도 이용권 발급이다.
- "강의 수강자만 참여하는 모임"(인프런 워밍업 클럽형)은 강의 이용권을 모임 참가 조건으로 거는 것이다.
- 멤버십도 기간·횟수가 붙은 이용권이다(동행클럽형).

## 결제 흐름 — 지금과 나중이 같은 길을 쓴다 (제안)

```text
신청(주문 생성, 입금 대기) ─▶ 입금 확인 ─▶ 결제 완료 ─▶ 이용권 발급
        │                     │
        └─ 기한 초과: 만료     ├─ 지금: 운영진이 확인 버튼(누가·언제 기록)
                               └─ 나중: PG 웹훅이 서버에서 검증
```

- 주문에 결제 수단(`계좌이체` / 나중에 `PG`)과 확인한 사람·시각을 남긴다.
- 환불과 취소도 주문 상태로 기록하고 지우지 않는다.
- 금액은 서버가 상품에서 다시 계산하고, 화면이 보낸 금액을 믿지 않는다.
- 호스트 정산은 플랫폼이 직접 결제를 받기 시작할 때 붙인다. 지금은 자리만 남긴다.

## 기술의 큰 틀 (제안)

- **화면**: 이 레포의 Next.js.
- **명령 계층**: 서버 액션과 라우트 핸들러. 도메인별로 `src/lib/<domain>/`에 둔다. 권한 확인과 검증은 여기서 한다.
- **저장**: Supabase(Postgres·Auth·Storage). RLS는 마지막 방어선으로 둔다.
- **외부 서비스**: 메일(Resend, 형제 서비스에서 사용 중), 나중에 PG.
- 별도 백엔드 서버는 아직 두지 않는다.

## 단계 (제안)

1. **계정·권한.** 로그인, 프로필, 운영진 역할.
2. **이용권 + 강의 진도 서버 저장.** 워크북 진도가 새로고침에도 남는다.
3. **모임 기본.** 그룹·회차·참가 신청, 무료부터.
4. **거래(계좌이체).** 신청 → 입금 확인 → 이용권. 형제 서비스의 클래스 신청을 여기로 옮긴다.
5. **호스트 도구.** 내 모임, 명단, 공지, 출석.
6. **플랫폼 직접 결제와 정산.** PG, 수수료, 호스트 정산, 통신판매 지위 정리.
