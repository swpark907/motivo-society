# 관리자 운영 정책과 프로젝트 분리 판단

2026-10-16. **승인 전 제안**이다. 기존 `admin-content-architecture.md`가 구현 경계를 설명했다면, 이 문서는 운영자가 어디로 들어오고 누구에게 무엇을 허용할지부터 판단한다. 이번에는 운영 코드·인증·계정을 변경하지 않는다.

## 1. 권장 결론

현재 규모에서는 **같은 저장소·같은 Next.js 앱·같은 배포에 `/admin`을 두고, 공개 화면과 관리자 화면의 레이아웃·서버 권한을 분리**하는 것을 권장한다. 운영자는 북마크한 `/admin`으로 진입하고, 초대받은 개인 계정으로 로그인한다. 운영 계정에는 MFA를 요구하고 일반 회원과 별도의 관리자 자격을 부여한다.

이 권장은 운영자가 소수이고 현재 관리 대상이 콘텐츠·소개 정보 중심이라는 전제다. 결제·회원 개인정보까지 같은 관리자 권한으로 넓히는 승인은 아니다. 현재 저장소에 운영 인증이 없으므로 `/demo/admin`을 그대로 운영에 노출하는 방식은 적절하지 않다.

## 2. ‘같은 프로젝트’는 세 가지 결정을 포함한다

| 선택                                 | 사용성·개발 비용                                                       | 보안·운영상의 실제 차이                                                                              | 현재 판단                            |
| ------------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 같은 저장소·같은 앱·`/admin`         | 렌더러·스키마 공유가 직접적. 배포·로그인 경로가 단순하다               | 공개 서비스와 서버 실행 환경·배포·장애 범위를 공유한다. 경로명으로 격리되지 않는다                   | **지금 권장**                        |
| 같은 저장소·별도 관리자 앱·별도 배포 | 공통 패키지로 렌더러 공유 가능. 두 배포·인증 콜백·환경 설정을 관리한다 | 호스트·세션·서버 자격 증명을 실제로 분리하면 노출과 장애 범위를 줄일 수 있다                         | 민감 업무나 운영 요구가 생길 때 검토 |
| 별도 저장소·별도 앱                  | 릴리스·코드 접근권을 독립 관리. 공유 패키지 버전 관리가 필요하다       | 저장소 분리만으로 데이터 권한이 분리되지는 않는다. 독립 자격 증명과 서버 권한 설계가 여전히 필요하다 | 현 단계 비용 대비 이점이 작다        |

`admin.도메인`이라는 주소만 추가하고 같은 서버·광범위한 쿠키·같은 자격 증명을 쓰면 강한 격리가 생겼다고 볼 수 없다. 반대로 같은 앱도 서버에서 요청마다 권한을 검사하면 운영할 수 있다. 다만 공개 앱의 서버 침해가 관리자 데이터에 영향을 줄 수 있는 공유 위험은 남는다.

별도 앱 전환을 검토할 시점은 외부 운영 대행사에 접근을 주거나, 결제·개인정보 업무를 운영하거나, 독립 배포/접속 제한 요구가 생기는 때다. 트래픽 증가 자체보다 권한·장애·운영 경계가 달라지는지가 기준이다.

## 3. 진입 방식과 사용 흐름

권장 흐름은 `/admin` → 로그인 → MFA → 서버의 활성 관리자 확인 → 원래 요청한 관리자 페이지다. 로그인된 일반 회원은 관리자 초대 안내나 콘텐츠 목록을 보지 않고 접근 권한이 없다는 안내와 공개 홈 이동만 본다. 로그인 전에는 관리자 데이터·초안 제목을 내려주지 않는다.

- 공개 GNB에는 관리자 메뉴를 넣지 않는다. 운영자는 북마크로 들어온다. 추후 계정 메뉴가 생기면 관리자 자격을 확인한 사람에게만 관리 링크를 표시할 수 있다.
- 숨겨진 주소는 접근 편의 정책이지 보안 장치가 아니다. `/admin` 존재가 알려져도 권한 없는 요청은 모두 거부돼야 한다.
- 로그인 후 복귀 주소는 같은 사이트의 허용된 관리자 경로만 받는다. 외부 URL로 보내지 않는다.
- 관리자 셸은 공개 GNB 대신 콘텐츠·미디어·홈 구성과 현재 계정·로그아웃을 제공한다. 공개 화면 확인 링크는 별도로 둔다.
- 문서를 닫거나 세션이 끝나도 작업을 잃지 않도록 초안 저장 상태를 표시한다. 운영 단계에서는 저장된 초안 복원이 필요하다. 현재 실험실의 새로고침 초기화는 운영 UX로 가져가지 않는다.
- 장시간 편집 중 재인증이 필요하면 내용을 보존하고 재로그인 후 복귀시킨다. 무조건 로그인 페이지로 보내며 작업을 버리지 않는다.

## 4. 계정 생성·회수 정책

**공개 관리자 가입은 제공하지 않고, 소유자의 초대로만 추가**하는 안을 권장한다. 공유 `admin` 아이디를 만들지 않고 사람마다 개인 계정을 사용한다. 인증은 검증된 제공자를 사용하며 자체 비밀번호 저장·복구 시스템은 만들지 않는다. 실제 로그인 제공자와 지원할 MFA 방식은 선정 전이다.

| 상황               | 제안 정책                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| 첫 소유자          | 배포 담당자가 승인된 신원을 배포/서버 관리 경로에서 최초 등록. 첫 방문자가 소유자가 되는 로직 금지            |
| 초대               | 소유자만 발급. 수신 신원·역할·만료·일회 사용을 묶고 로그인 후 검증된 신원과 연결                              |
| 계정 식별          | 제공자의 변경되지 않는 사용자 ID로 연결. 이메일은 초대·연락에 사용하고 매 요청의 권한 기준으로 삼지 않음      |
| 역할 변경          | 소유자만 수행. 최근 MFA 재확인과 감사 기록. 클라이언트가 보낸 role은 신뢰하지 않음                            |
| 중지/퇴사          | 관리자 자격 즉시 중지, 기존 세션/갱신 권한 회수. 다음 관리자 요청부터 거부. 작성·발행 이력의 개인 식별은 보존 |
| MFA 분실           | 사전에 발급한 복구 수단과 인증 제공자의 복구 절차 사용. 이메일 요청만으로 MFA를 해제하지 않음                 |
| 유일한 소유자 분실 | 운영 런북에 승인자·신원 확인·제공자/서버 복구·감사 기록 절차를 마련. 사이트 내 우회 로그인은 두지 않음        |
| 마지막 소유자      | 마지막 활성 소유자를 스스로 삭제/강등할 수 없게 함. 비상 복구 책임자를 사전 지정                              |

회원 서비스가 나중에 생겨도 로그인 신원은 공유할 수 있지만, **회원/유료 회원 여부와 관리자 자격은 별개**다. 형제 서비스 계정이 자동으로 여기의 관리자가 되어서는 안 된다. 기존 회원 통합 여부는 이 결론으로 확정하지 않는다.

## 5. 역할과 운영 책임

처음부터 자유로운 권한 조합 화면을 만들기보다 세 역할로 시작하는 안이다. 내부 서버 검사는 역할 문자열 대신 작업 권한으로 모아두면 이후 변경하기 쉽다.

| 역할        | 초안·미디어 편집 | 검토·발행·철회·홈 노출 | 계정 초대·권한 회수 |
| ----------- | ---------------- | ---------------------- | ------------------- |
| 소유자      | 가능             | 가능                   | 가능                |
| 발행 관리자 | 가능             | 가능                   | 불가                |
| 편집자      | 가능             | 불가                   | 불가                |

초기 실제 운영자가 한 명이면 소유자만 등록해 시작해도 된다. 역할을 채우기 위해 계정을 늘릴 필요는 없다. **자기 글의 검토·발행은 소유자/발행 관리자에게 허용하되, 실제 확인 근거를 직접 기록**하는 안을 추천한다. 2인 승인 강제는 소수 운영에서 병목이 되므로 지금은 제안하지 않는다. 대신 AI 생성·스키마 통과를 사람의 사실 검증으로 간주하지 않는다.

정식 발행이 기존 PR 검토 관문을 대체하려면 이 검토 기록 정책을 명시적으로 승인해야 한다. 그 전에는 관리자 편집기 추가만으로 기존 발행 규약을 없애지 않는다. 가격·환불 정책 변경은 기존 대표 승인 규칙을 그대로 따른다.

## 6. 같은 앱을 선택할 때 필요한 보안 경계

로그인은 신원 확인이고 관리 권한은 별도 판단이다. 기본 거부와 요청별 권한 확인이 기준이다. Next.js도 layout 검사만으로 보호하지 말고 데이터 접근 계층과 서버 동작에서 확인하도록 안내한다. [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication), [OWASP 권한 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

1. 관리자 데이터 조회·저장·발행 각각에서 서버가 세션, 활성 관리자 자격, 필요한 권한을 확인한다. layout이나 Proxy의 리다이렉트는 조기 안내이며 최종 통제가 아니다.
2. 관리자 권한은 서버 저장소를 기준으로 확인한다. 장기 토큰의 오래된 역할만 믿으면 권한 회수가 늦어질 수 있다. 계정 중지를 반영하는 검증·세션 폐기 방식을 제공자 선택 때 확인한다.
3. 관리 세션은 HTTPS·HttpOnly·Secure 쿠키 등 제공자의 안전한 세션 처리를 사용한다. MFA는 서버에서 확인하고, 발행·계정 변경 같은 민감 동작의 재인증 정책을 둔다. 권장 시간 초안은 유휴 30분/절대 12시간, 계정 변경 시 최근 10분 이내 MFA다. 이 수치는 표준의 요구가 아니라 운영 제안이며 자동 저장과 함께 시험한다. [OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), [세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
4. 변경 요청은 프레임워크의 출처 검증을 유지하고, 별도 API를 만들면 해당 API에도 CSRF 방어를 둔다. GET 요청으로 저장·발행하지 않는다. 인증 실패·초대·복구 요청에는 속도 제한을 둔다.
5. 공개 조회는 공개 개정본만 읽는다. 초안·개인 계정·관리 응답은 공유 캐시나 공개 정적 산출물에 섞지 않는다. 초안 프리뷰도 인증을 요구한다. 외부 공유 프리뷰는 별도 정책 전까지 제공하지 않는다.
6. 편집 JSON은 제한된 데이터로 렌더링한다. 임의 MDX/JSX 코드를 관리자 입력으로 실행하지 않는다. 업로드 도입 때 파일 형식·용량·실제 내용·저장 경로 검증을 별도로 설계한다.
7. 서버 비밀키는 클라이언트에 보내지 않고 공개 조회와 관리 쓰기 권한을 저장소에서 가능한 범위까지 구분한다. 같은 런타임의 광범위한 서버 침해까지 코드 폴더만으로 막을 수는 없다.
8. 초대·역할 변경·초안 저장·발행·철회는 누가 언제 무엇을 했는지 서버 이력으로 남긴다. 토큰·비밀번호·복구 코드는 로그에 남기지 않는다. 발행 취소와 데이터 복구를 배포 전 검증한다.

이 항목들은 운영 전환의 수용 조건이다. 현재 실험실에 구현돼 있다는 뜻이 아니다.

## 7. 권장 정책에 비춰 본 현재 코드

| 현재 상태/증거                                                              | 판정                                               | 필요한 변화                                                                 |
| --------------------------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------- |
| 하나의 Next.js 앱, 인증 SDK·관리 API 없음 (`package.json`, `src/app`)       | 같은 앱으로 확장 가능. 운영 준비 완료는 아님       | 인증 제공자 연결, 관리자 자격 저장소, 서버 권한 함수 추가                   |
| `src/app/layout.tsx`가 GNB를 전 페이지에 출력                               | 관리자 UX에는 부적합                               | 공개 GNB를 `(public)/layout`으로 이동하고 `/admin` 전용 셸 분리. URL은 보존 |
| `src/lib/nav.ts`에 공개 메뉴만 있음                                         | 적절                                               | 관리자 내비게이션을 공개 목록에 섞지 않기                                   |
| `/demo/admin`·`/demo/editorial-preview`가 development 전용                  | 실험실로 적절                                      | 조건을 지우며 운영 전환하지 않기. `/admin`에 실제 접근 통제를 새로 연결     |
| `EditorialArticle`, 스키마, 순수 편집 로직이 분리됨                         | 같은 앱 선택에 유리                                | 공통 유지. 추후 별도 앱이 되면 이 부분을 공유 패키지로 옮길 수 있음         |
| 편집기 상태가 탭 메모리, JSON 다운로드만 제공                               | 테스트로 적절. 운영 편집기로 부족                  | 서버 초안 저장·충돌 처리·재인증 복귀·복원 기능 필요                         |
| `validateEditorialDraft`가 다섯 샘플·사진 목록에 묶임                       | 샘플 안전장치로 적절. 운영 검증 경계로 부족        | 스키마 검증과 운영 콘텐츠/자산 조회 검증을 분리하고 서버에서도 재검증       |
| 정식 아티클은 파일 MDX + PR 검토 (`src/lib/content/articles.ts`, AGENTS.md) | 현 운영과 일치. 관리자 저장·발행과 아직 연결 안 됨 | DB 기반 전환 여부와 검토 관문 대체를 먼저 승인. 공개 URL·기존 글 보존       |
| 공개 읽기 로직이 `src/lib/content/` 뒤에 있음                               | 저장소 변경에 유리                                 | 페이지가 관리자 저장소를 직접 읽지 않고 공개 개정본 조회 계약을 유지        |

**판정: 현재 구조는 이 정책으로 확장할 출발점으로 적절하지만, 현재 실험실을 보안된 관리자라고 부를 단계는 아니다.** 전면 재작성이나 별도 저장소는 필요하지 않다. 공통 레이아웃, 서버 권한 경계, 계정 수명주기, 영속 초안·발행 흐름은 운영 전환 때 보완해야 한다.

## 8. 결정 순서

먼저 같은 앱의 `/admin`이라는 배치, 초대형 개인 계정+MFA, 세 역할, 자기 글 검토 허용 여부를 합의한다. 다음으로 첫 운영자·복구 책임자와 로그인 제공자·관리자 자격 저장소를 정한다. 이 선택에는 실제 사용할 계정 종류, MFA·복구·세션 회수 지원, 기존 서비스 통합 필요를 비교해야 한다.

그 후에 서버 접근 통제와 계정 회수 검증 → 초안 저장·복원 → 검토·발행 및 기존 PR 관문 이관 → 미디어·홈 구성 순서로 연결한다. 인증을 붙인 것만으로 발행을 먼저 열지 않는다. 별도 앱 분리 여부는 민감 업무·독립 운영 요구가 생겼을 때 재검토한다.

이 문서의 추천들은 사용자 승인 전까지 확정 정책이나 AGENTS.md의 구현 지시로 옮기지 않는다.
