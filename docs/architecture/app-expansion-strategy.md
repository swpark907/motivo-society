# 앱 확장 전략 (2026-11-13)

플랫폼은 웹에서 시작해 최종적으로 모바일 앱과 앱 푸시까지 간다(커뮤니티 기획의 "웹 우선 → 모바일 앱"). 이 문서는 그 길의 순서와, 지금부터 해 둘 준비를 정한다. 2026-11-13 승우가 이 방향을 승인했다. 단계를 넘어가는 시점과 세부 기술 선택은 그때 다시 정한다.

## 1. 순서

| 단계                               | 무엇                                                                                                              | 넘어가는 신호(예시)                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **0. 웹 + PWA (지금)**             | 반응형 웹을 설치형 웹앱(PWA: 매니페스트 + 서비스 워커)으로. 홈 화면에 추가하면 앱처럼 열리고 **웹 푸시**를 받는다 | —                                                                     |
| **1. 감싼 앱으로 스토어 진입**     | 지금 웹 화면을 앱 껍데기(Capacitor 등)에 넣고, 푸시·딥링크 같은 네이티브 기능만 붙인다                            | iOS 사용자가 홈 화면 추가를 안 해 알림이 닿지 않음 · 모바일 비중이 큼 |
| **2. React Native(Expo)로 옮기기** | 매일 여는 화면(채팅 · 일정 · 인증 · 클럽 홈)부터 앱 화면으로 새로 만든다. Supabase · 타입 · 로직은 공유           | 앱이 서비스의 중심이 됨 · 감싼 앱의 손맛·성능이 한계                  |

완전 네이티브(Swift/Kotlin)는 지금 규모에서 검토하지 않는다.

**넘어가는 시점은 날짜가 아니라 신호로 정한다.** 볼 숫자: 알림 도달률(웹 푸시 구독·홈 화면 추가 비율), 모바일 접속 비중, 주간 활성 회원, 채팅 사용량.

### 1단계(감싼 앱)의 주의점

- 애플 심사는 "웹사이트를 감쌌을 뿐인 앱"을 거절할 수 있다. 앱 푸시 · 딥링크(초대 링크로 앱 열기) · 공유처럼 **앱이라서 되는 기능**을 함께 넣는다.
- Next.js 서버 렌더링 화면을 그대로 쓰면 앱이 원격 주소를 띄우는 방식이 된다. 오프라인에서는 쓰기 어렵다는 점을 받아들인다.

## 2. 지금부터 해 둘 준비 (비용이 작고, 나중에 크게 덜 아프다)

1. **로직은 화면 밖에.** 도메인 로직은 `src/lib`(React 없음), 데이터 규칙은 Supabase 함수·RLS에 둔다. 앱이 같은 함수를 그대로 부른다. 지금 구조가 이미 이렇다 — 유지한다.
2. **영구 주소 = 딥링크.** `/activities/[slug]`, `/clubs/[slug]`, `/invite/[code]`는 바꾸지 않는다(영구 주소 규칙). 앱 단계에서 이 주소가 그대로 앱을 연다(유니버설 링크·앱 링크).
3. **알림은 "일어난 일"과 "보내는 길"을 나눈다.** 알림 기록(누구에게 · 무슨 일 · 읽음)을 한 테이블에 쌓고, 보내는 길(지금 웹 푸시 → 나중에 앱 푸시)은 바꿔 끼우는 부품으로 만든다. 앱이 생기면 길만 하나 더한다. 사람마다 알림 종류를 켜고 끈다.
4. **로그인 방식 보강.** 매직링크는 앱에서 불편하다(메일의 링크가 브라우저로 열린다). **이메일 인증번호(6자리)** 와 비밀번호 로그인을 함께 둔다. motivo.kr 기존 회원(비밀번호 사용)의 흡수에도 필요하다(`landing-absorption-plan.md`).
5. **하단 탭 다섯 자리.** 웹 GNB와 앱 하단 탭이 같은 다섯 자리(홈 · 둘러보기 · 클럽 · 클래스 · MY)를 쓴다. 정의는 `src/lib/nav.ts` 하나. 모바일 앱 문법 시안은 `/demo/design-mobile`.
6. **이미지·파일은 크기별로.** 표지·사진은 앱에서도 쓰므로 원본과 작은 크기를 함께 두는 지금 방식을 유지한다.

## 3. 앱 안 결제 — 앱 단계 전에 꼭 확인

- **모임 · 시즌 · 챌린지 참가비:** 앱 밖에서 이루어지는 실물 서비스라 스토어 결제 대상이 아닌 경우가 많다.
- **워크북 같은 디지털 클래스:** 앱 안에서 팔면 애플·구글 결제(수수료가 크다)를 써야 할 수 있다. 앱에서는 수강(보기)만 하고 구매는 웹에서 하는 방식도 검토한다.
- **호스트 월정액(9,900원):** 앱 안에서 결제하게 할지에 따라 같은 문제가 생긴다. 웹에서 받는 것을 기본으로 둔다.
- 규정은 나라·시기마다 바뀐다. 앱 단계 진입 전에 그 시점의 스토어 규정을 직접 확인한다(이 문서는 확인 전 메모다).

## 4. 열린 것

- 1단계 진입 신호의 구체적인 기준값.
- 1단계 도구(Capacitor 외 후보) 선택.
- 2단계로 옮길 화면의 순서.
- 앱 안 결제 처리 방식(3절).
