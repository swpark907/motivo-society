# 워크북 수업 만들기

규칙은 이 파일에 두지 않는다(Codex도 같은 규칙을 봐야 하므로). 시작할 때 아래 문서를 읽고 그대로 따른다.

1. `docs/product/workbook-lesson-authoring.md` — 기획·원고·연출·구현·확인 규칙 전부
2. `AGENTS.md`의 "Workbook 경험 원칙" — 최신 결정
3. 해당 단원의 기획 문서(1단원은 `docs/product/workbook-unit-1-plan.md`, 2단원은 `docs/product/workbook-unit-2-plan.md`) — 화면 흐름표와 이미 정한 것

## 작업 순서

1. **흐름표 확인 또는 작성.** 기획 문서에 그 수업의 화면 흐름표(번호 · 제목 · 핵심 문장 · 표현 방식)가 있으면 따른다. 없으면 기획자의 주제 흐름을 받아 표로 정리해 보여준다. 기획자가 흐름을 직접 내면 그 흐름을 쓴다.
2. **화면마다 제안.** 무엇을 어떻게 보여주고 어떻게 움직일지 한두 개 대안과 고른 이유를 붙여 제안한다. 앞뒤 화면과 표현 방식이 겹치지 않는지, 큰 연출이 핵심 화면에만 있는지 함께 본다. 확정 전에는 구현하지 않는다.
3. **한 화면씩 구현.** 기획자가 고른 화면 하나를 실제 워크북 수업에 넣는다(데모 경로가 아니라). 사실이 들어가는 화면은 구현 전에 공식 자료로 확인한다.
4. **확인.** 규칙 문서의 "확인" 절대로: PC·모바일 화면, 모션 중간 장면, `pnpm check`, 흐름이 바뀌었으면 해당 e2e.
5. **보고와 갱신.** 무엇을 했고 어떻게 확인했는지, 확인하지 못한 것을 보고한다. 기획 문서의 흐름표 칸을 "(구현됨)"으로 고친다. 이번에 새로 정한 규칙은 `docs/product/workbook-lesson-authoring.md`에 추가한다.
6. **다음 화면으로.** 기획자의 피드백을 반영한 뒤 다음 화면을 묻는다. 커밋은 기획자가 끝났다고 할 때만 한다.
7. **수업을 다 만들면 전수 점검.** 규칙 문서 7절의 순서(사실과 다르게 남는 것 → 흐름과 내용 → 표현과 디자인 → 접근성과 동작 → 문구만 따로 → 코드 리뷰)대로 본다. 묶음마다 찾은 것을 번호와 제안으로 보고하고, 기획자가 고르면 고친다. 점검에서 새로 나온 종류의 문제는 규칙 문서에 더한다.

## 만들면서 늘 대 볼 것 (자세한 이유는 규칙 문서)

- 첫 화면은 결론이 아니라 지금 자리 → 일상 장면 → 발견.
- 한 화면에 한 가지 일(배우기와 직접 쓰기를 나눈다). 누를 것은 적게.
- 수업 제목 · 구성안도 학습자가 아는 말로 하는 일을 쓴다("너비" 같은 만드는 사람의 말 금지). 기획자에게 낼 때부터.
- 비유어는 정체를 밝히고 같은 말로. 지시어엔 대상과 장소를. 이유 없는 단계는 이유를 붙이거나 뺀다.
- 워크북 밖 실습은 "보내고 → 확인"까지 끝까지 적는다. 앞 수업의 원칙을 예시가 어기지 않는다.
- 예시는 학습자의 기록·복사로 들어가지 않는다. 근거 없는 기록을 만들지 않는다. 도장은 되돌릴 수 있게.
- Windows · Mac은 실제로 다를 때만 나눈다. 같은 성격 표시는 "(연습)"으로.
- 손글씨는 짧은 말에만. 색은 `--workbook-*` 토큰. 수업 번호·이름은 `workbook-course.ts`에서.
- 학습자가 만드는 결과물은 실제처럼 그리고, 고를 때마다 바뀌게. 회색 막대 · 점선 칸만으로 그리지 않는다. 예시 페이지도 실제 사이트처럼.
- 카피바라 장면은 단원에 두세 곳. 같은 틀("설명 + 버튼 묶음 + 상자")을 화면마다 반복하지 않는다.
- 정리 화면은 수업마다 주제에 맞는 물건 하나. 알게 된 것은 굵은 한 줄 + 설명, 다음 수업은 한 줄.
- 못 넘어갈 때는 흐린 버튼에 짧은 이유, 빈 자리마다 "어디서 채우는지" 빨간 글자 링크.
- 단원을 다 만들면 앞 단원 화면과 같은 크기로 나란히 찍어 비교한다.
